Run Gemma4-MoE on the Hexagon NPU

This guide takes you from a Linux PC and an Android phone to a first Gemma4 26B-A4B response, using either the command line or the Quick.AI Android app. It covers installing the toolchains, building nntrainer, installing the runtime, copying a model pack, and checking that the NPU actually runs the model.

Source baseline: PR #4480, commit 67d2903a279a3f5604074f001bbf8f814dfb9f82, reviewed on 2026-11-05. Commands below target that revision, including the SDK/HexKL 6.4.0.1 pairing, the updated Metrics benchmark and the 2,304-position Gemma4 chat preset. Screenshot and benchmark dates are recorded separately below. A different checkout may have different commands or features.

You need a separately supplied, ready-to-run Gemma4 HTP model pack. Neither this repository nor the APK includes the weights. No public download URL for the delivered pack is documented in this PR. Obtain the pack and its matching configuration from your model provider before attempting inference. Downloading an ordinary Hugging Face checkpoint is not a replacement for this step.

All bash blocks run in Bash on the Linux PC, including commands beginning with adb. Blocks marked sh run inside adb shell on the phone. Replace example paths with your own absolute paths. Continue in the same host terminal so that exported environment variables remain available. Stop and resolve an error before moving to the next step.

1. Check the requirements

Component Version or requirement used by this guide
Build PC Ubuntu 24.04, x86-64; reserve about 60 GB for tools and builds, plus space for the model pack and archives
Phone Galaxy S26 Ultra, Snapdragon SM8850, Hexagon v81, Android 16 with 4 KB memory pages, as documented by the PR
NPU compatibility HEX_ARCH=v81 is required. A Qualcomm NPU alone does not establish compatibility; other DSP generations and 16 KB-page devices are outside the validated baseline
Minimum Android version App installation requires API 33 (Android 13) or newer. The NPU validation baseline is the phone environment above
Hexagon SDK 6.4.0.1, including Hexagon Tools 19.0.04
Hexagon Kernel Library (HexKL) 1.0 beta2, using its lib/6.4.0.1 libraries
Android NDK r30, package revision 30.0.16248370
Android app tools JDK 17, SDK platform 36, build-tools 36.0.0, SDK CMake 3.22.1, platform-tools
Native build tools GCC/G++, Meson, Ninja, CMake, Python 3, Rust/Cargo, Git

Working memory (RAM) Separate from storage; usage depends on context length and expert cache settings. Use the provider's phone-tested settings for the first run and close other memory-heavy apps

What the components do

  • Android NDK: compiles the ARM64 code that runs on the phone's CPU.
  • Hexagon SDK and Tools: compile and connect to the DSP/NPU code through FastRPC.
  • HexKL: supplies kernels used by the Hexagon backend, called HTP in nntrainer.
  • libnntr_hvx_skel.so: nntrainer's DSP program, built from this PR. It must match the ARM-side libraries from the same build.
  • QuickDotAI / Quick.AI: the reusable Android library (AAR) and sample application (APK), respectively.

This guide uses --htp; a QNN SDK installation is not required. The latest script also supports --qnn --htp for a combined package, which additionally requires the QNN dependencies. OpenCL is enabled by default; use --disable-opencl consistently across build/install commands if you want a package without the OpenCL/GPU backend.

2. Install the Linux and Android tools

Linux build dependencies

sudo apt update
sudo apt install -y \
  build-essential git curl wget unzip zip file pkg-config \
  python3 python3-pip python3-venv meson ninja-build cmake \
  openjdk-17-jdk autoconf automake libtool

export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"
java -version
python3 --version
meson --version
ninja --version
cmake --version

java -version should report Java 17. These commands install host build tools; the NDK supplies the Android compilers. Do not install a host nntrainer package as a substitute for the Android build below.

Install Rust using the official rustup installer, accepting the default installation when prompted:

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/nntr-rustup-init.sh
sh /tmp/nntr-rustup-init.sh
source "$HOME/.cargo/env"
rustup target add aarch64-linux-android
rustc --version
cargo --version

Rust builds the repository's tokenizer library. The build script manages the Android C/C++ compiler settings for that library; no separate tokenizer checkout or cargo-ndk installation is needed.

Android SDK and NDK

Download Command line tools only → Linux from the Android Studio downloads page. Extract the archive into a temporary directory. Place its contents so that the SDK manager is at $HOME/Android/Sdk/cmdline-tools/latest/bin/sdkmanager, as in Google's SDK manager instructions. For example, replacing the archive name with the one you downloaded:

export ANDROID_HOME="$HOME/Android/Sdk"
export NNTR_ANDROID_TOOLS_ZIP="$HOME/Downloads/commandlinetools-linux-REPLACE_ME_latest.zip"
NNTR_ANDROID_TOOLS_TMP=$(mktemp -d)
unzip "$NNTR_ANDROID_TOOLS_ZIP" -d "$NNTR_ANDROID_TOOLS_TMP"
mkdir -p "$ANDROID_HOME/cmdline-tools/latest"
cp -a "$NNTR_ANDROID_TOOLS_TMP/cmdline-tools/." "$ANDROID_HOME/cmdline-tools/latest/"
export PATH="$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH"
sdkmanager --version

If Android Studio already installed the SDK, use its SDK location instead and install Android SDK Command-line Tools from its SDK Manager. Keep ANDROID_HOME and any existing ANDROID_SDK_ROOT pointed at the same directory. The commands here use the SDK manager shipped in the command-line tools package.

Install the pinned packages, review and accept the Android licenses:

sdkmanager --sdk_root="$ANDROID_HOME" --licenses
sdkmanager --sdk_root="$ANDROID_HOME" \
  "platform-tools" "platforms;android-36" "build-tools;36.0.0" \
  "cmake;3.22.1" "ndk;30.0.16248370"

export ANDROID_NDK="$ANDROID_HOME/ndk/30.0.16248370"
cat "$ANDROID_NDK/source.properties"
"$ANDROID_NDK/toolchains/llvm/prebuilt/linux-x86_64/bin/clang" --version
adb version

The NDK revision should be 30.0.16248370, corresponding to NDK r30. If using the standalone android-ndk-r30-linux.zip instead, extract it and set ANDROID_NDK to the resulting android-ndk-r30 directory. The app build uses the same NDK path as the native build. The repository provides its Gradle wrapper; do not install a separate system Gradle.

3. Install Hexagon SDK and HexKL beta2

Get the Qualcomm packages

Use the official Qualcomm Software Center Hexagon SDK catalog and Qualcomm Package Manager entry points. Sign in with your Qualcomm account when requested. Select Hexagon SDK 6.4.0.1 for Linux and install its Hexagon Tools 19.0.04 component. Use the installer's reported destination; the examples below use $HOME/Qualcomm/Hexagon_SDK/6.4.0.1.

If the portal requires the Linux Package Manager application, download its Debian package, install that downloaded file, then open the application and sign in:

# Replace the filename with the package you actually downloaded.
sudo apt install "$HOME/Downloads/QualcommPackageManager3.3.0.133.0.Linux-x86.deb"

In the Qualcomm catalog, also locate Hexagon Kernel Library (HexKL) and select 1.0 beta2. It is distributed separately from the SDK. The Qualcomm AI Stack catalog is another entry point to this package. Portal screens and version availability depend on your account. If the required version is unavailable, request access from Qualcomm or your package provider; do not silently replace it with another release. There is no anonymous package-download URL assumed by this guide.

Extract the supplied beta2 ZIP. This example uses the archive name hexkl-1.0-beta.2.zip, whose top-level directory is hexkl_addon:

mkdir -p "$HOME/Qualcomm/HexKL/1.0-beta2"
unzip "$HOME/Downloads/hexkl-1.0-beta.2.zip" -d "$HOME/Qualcomm/HexKL/1.0-beta2"
export HEXKL_ROOT="$HOME/Qualcomm/HexKL/1.0-beta2/hexkl_addon"
head -n 8 "$HEXKL_ROOT/README.md"

The README should identify 1.0 Beta.2. If your download has an additional outer archive, extract it first and point HEXKL_ROOT at the directory that actually contains include/ and lib/.

Set the environment

On the host, source the installed SDK's environment script first, then set the Android and HexKL paths explicitly:

source "$HOME/Qualcomm/Hexagon_SDK/6.4.0.1/setup_sdk_env.source"

export HEXKL_ROOT="$HOME/Qualcomm/HexKL/1.0-beta2/hexkl_addon"
export HEXKL_SDK_VER=6.4.0.1
export HEXKL_TOOLS_VARIANT=toolv19
export HEXKL_ARCH=armv8_android26
export HEX_ARCH=v81
export ANDROID_HOME="$HOME/Android/Sdk"
export ANDROID_NDK="$ANDROID_HOME/ndk/30.0.16248370"
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
export PATH="$JAVA_HOME/bin:$HOME/.cargo/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH"

setup_sdk_env.source supplies HEXAGON_SDK_ROOT and DEFAULT_HEXAGON_TOOLS_ROOT. If you installed the SDK elsewhere, change the source path. Re-run this block whenever you start a fresh terminal, or save these commands in a shell file outside the source checkout and source it.

Use 6.4.0.1 for both the Hexagon SDK and the HexKL library selection. HexKL's lib/<version> directory names the SDK version the libraries target. HEXKL_SDK_VER=6.4.0.1 selects lib/6.4.0.1: the Android runtime is armv8_android26/libsdkl.so, and the DSP build links hexagon_toolv19_v81/libhexkl_micro.a below it. Both build scripts default to this version. The DSP script no longer selects the newest available directory automatically. Check that the matching directory exists; do not rename a different version's directory to make the path check pass.

Check the paths before building:

printf 'SDK: %s\nTools: %s\nHexKL: %s\n' \
  "$HEXAGON_SDK_ROOT" "$DEFAULT_HEXAGON_TOOLS_ROOT" "$HEXKL_ROOT"

ls "$HEXAGON_SDK_ROOT/setup_sdk_env.source" \
   "$HEXAGON_SDK_ROOT/rtos/qurt/computev81/include/qurt" \
   "$HEXKL_ROOT/include/hexkl_micro.h" \
   "$HEXKL_ROOT/lib/$HEXKL_SDK_VER/armv8_android26/libsdkl.so" \
   "$HEXKL_ROOT/lib/$HEXKL_SDK_VER/hexagon_toolv19_v81/libhexkl_micro.a"

"$DEFAULT_HEXAGON_TOOLS_ROOT/Tools/bin/hexagon-clang" --version

Every path must exist, and the compiler must be the Tools 19.0.04 installation. DEFAULT_HEXAGON_TOOLS_ROOT names the directory above Tools/, not Tools/bin. HexKL provides prebuilt libraries: building all of its examples is not required for nntrainer. Its generic libhexkl_skel.so is not a substitute for nntrainer's libnntr_hvx_skel.so.

4. Get the PR source and connect the phone

Use a separate checkout

On the host, use a new directory so an existing project is not overwritten:

mkdir -p "$HOME/workspace"
cd "$HOME/workspace"
git clone https://github.com/nntrainer/nntrainer.git nntrainer-gemma4-pr4480
cd nntrainer-gemma4-pr4480
git fetch origin pull/4480/head
git switch --detach 67d2903a279a3f5604074f001bbf8f814dfb9f82
git submodule sync --recursive
git submodule update --init --recursive --depth 1
export NNTR_ROOT="$PWD"
git rev-parse HEAD

The hash should match the source baseline at the top of this guide. This pins instructions to a known revision even if the PR later changes. Submodules are required for the build; initializing them is different from editing their vendored source. Downloads also occur during the first tokenizer and Gradle builds, so keep internet access available.

Authorize ADB

On the phone, enable Developer options by tapping Build number seven times (on Samsung: Settings → About phone → Software information). Enable USB debugging in Developer options, connect a data-capable USB cable, and accept the debugging authorization prompt on the unlocked phone.

On the host:

adb devices -l

The device must be listed as device, not unauthorized or offline. When more than one device or emulator is connected, set the serial shown in that output:

# Replace this value with the serial from adb devices -l.
export ANDROID_SERIAL=REPLACE_WITH_DEVICE_SERIAL
adb get-state
adb shell getprop ro.product.model
adb shell getprop ro.soc.model
adb shell getprop ro.build.version.release
adb shell getconf PAGE_SIZE
adb shell df -h /sdcard

If only one device is attached, ANDROID_SERIAL can remain unset. Expected baseline: S26 Ultra / SM8850, Android 16, page size 4096. Build and runtime compatibility still depend on the device's firmware and FastRPC support; these properties alone do not prove NPU execution. No adb root step is required by this workflow.

5. Build and install the native runtime

Build first

On the host:

cd "$NNTR_ROOT/Applications/CausalLM"
set -o pipefail
./build_android.sh --htp 2>&1 | tee "$NNTR_ROOT/gemma4-htp-build.log"

The script generates the FastRPC stub, builds the v81 DSP image, builds the Android engine and tokenizer, and then builds the CausalLM tools. The DSP build checks its symbols and architecture; successful output includes ARCH OK (V81). The final message should be Done (native htp build) with the artifact directory. A failed command piped through tee still fails because pipefail is enabled.

Output Location relative to NNTR_ROOT Purpose
nntr_causallm builddir_app/htp/ Direct model-pack CLI
quick_dot_ai_test builddir_app/htp/ C API runner and optional lifecycle test
libcausallm.so, libquick_dot_ai_api.so builddir_app/htp/ Model runtime and public API
libnntrainer.so, libccapi-nntrainer.so builddir/android_build_result/lib/arm64-v8a/ nntrainer engine
libnntr_hvx_skel.so nntrainer/tensor/htp_backend/dsp/build/ v81 DSP program
nntr_quantize, nntr_safetensors_info builddir_app/htp/ Additional tools; the quantizer does not create this HTP pack

Check the two essential executables and the DSP image:

cd "$NNTR_ROOT"
ls -lh builddir_app/htp/nntr_causallm \
  builddir_app/htp/quick_dot_ai_test \
  nntrainer/tensor/htp_backend/dsp/build/libnntr_hvx_skel.so
file builddir_app/htp/nntr_causallm

The CLI is an ARM aarch64 executable. Run it on the phone, not directly on the x86-64 PC.

Install on the phone

On the host, with the authorized phone connected:

cd "$NNTR_ROOT/Applications/CausalLM"
./build_android.sh --htp --cache --install
adb shell ls -lh /data/local/tmp/Quick.AI

--cache reuses a compatible engine build; the script still performs the remaining build steps. --install deploys executables and runtime libraries to /data/local/tmp/Quick.AI, replacing its managed runtime files, and creates run_causallm.sh and run_test.sh wrappers. It does not copy the model pack.

The runtime includes libsdkl.so from HexKL and libc++_shared.so from the NDK. The phone supplies libcdsprpc.so from its vendor partition. Rebuild and deploy the ARM libraries, stub and DSP image together; copying only an old DSP image into a new build can break their shared protocol.

--clean recreates the selected CausalLM native build directory; it is not a promise to remove every engine or Gradle cache. The default HTP CPU thread count is 8; leave it unchanged for the first run.

The latest script also accepts --stage to assemble the public native files under builddir_app_stage/public/htp/ with a sibling .manifest.json report. --stage=DIR selects a dedicated directory that the script recreates on each run. This is useful for library integration; the app build handles its own staging. --cache also checks the OpenCL setting before reusing an engine.

6. Prepare and copy the model pack

Ask your model provider for a chat-ready Gemma4 26B-A4B HTP pack compatible with this PR. Keep the delivered weights, rotations, tokenizer and config files together. This guide does not create or quantize weights.

The latest catalog has three Gemma4 HTP entries. The commands in this guide use the first row; choose another only with its matching supplied pack.

Catalog ID App FAMILY / MODEL VARIANT Directory below BASE PATH
gemma4-26b-a4b-htp gemma4-26b-a4b / Gemma4 26B A4B MoE (HTP) gemma4-26b-a4b-htp-w4a32/
gemma4-26b-a4b-htp-long gemma4-26b-a4b / Gemma4 26B A4B MoE (HTP, 30k demo) gemma4-26b-a4b-htp-long-w4a32/
gemma4-26b-a4b-htp-2bit-4bit gemma4-26b-a4b-2bit-4bit / Gemma4 26B A4B MoE (HTP, rotated 2/4-bit) gemma4-26b-a4b-2bit-4bit/

Selecting the 30k demo does not expand an ordinary pack's context or establish that the phone has enough RAM. Keep the provider's matching settings.

The app expects this layout on the phone:

/sdcard/Download/aistudio-mobile/models/       ← model base path
└── gemma4-26b-a4b-htp-w4a32/                 ← model pack directory
    ├── nntr_config.json
    ├── config.json
    ├── tokenizer.json
    ├── chat_template.jinja
    ├── generation_config.json
    ├── <weight file named by model_file_name>
    └── <any sidecars named in nntr_config.json>

config.json must be the flat text-model configuration, not a wrapper containing only text_config. The provider's nntr_config.json selects htp_fused / htp_fused_v1, the engine assignments and the actual weight formats.

Two Gemma4 pack families exist in this PR:

Pack Expert format Projections / head
Delivered palette pack QS2CX_WH QS4CX projections, tied Q4_0 head on CPU
Native ternary pack TL2CX_WH, possibly mixed affine expert layers QS4CX_WH_AFFINE projections and untied HTP head

The app's W4A32 label is a catalog selection, not a statement that every tensor has four-bit weights. Do not change dtype names to match that label. In particular, do not overwrite a TL2 pack's nntr_config.json with the palette preset from Applications/CausalLM/res/gemma4/htp_chat/. For a palette pack requiring a chat preset, confirm its weights match that preset with the provider before replacing config files. The PR's model-pack contract describes the formats and optional sidecars in detail.

When updating an older pack for this revision, follow the removed-switch migration notes. Retired nested htp / moe keys are rejected at load. Remove the listed keys from a compatible copy of the pack configuration; do not replace TL2 settings with a palette preset. The retired moe.hadamard=both_scalar value becomes both when that same rotation is required by the checkpoint.

On the host, set the directory of the supplied pack and check the main files:

export NNTR_MODEL_PACK="$HOME/models/gemma4-26b-a4b-htp-w4a32"
python3 - <<'PY'
import json
import os
from pathlib import Path

pack = Path(os.environ["NNTR_MODEL_PACK"])
for name in ("nntr_config.json", "config.json", "tokenizer.json",
             "chat_template.jinja", "generation_config.json"):
    path = pack / name
    if not path.is_file():
        raise SystemExit(f"Missing chat-pack file: {path}")
cfg = json.loads((pack / "nntr_config.json").read_text())
weights = pack / cfg["model_file_name"]
if not weights.is_file() or weights.stat().st_size == 0:
    raise SystemExit(f"Missing or empty weights: {weights}")
print("Weight file:", weights.name)
print("Weight bytes:", weights.stat().st_size)
print("Expert format:", cfg.get("moe_layer_dtype"))
print("Execution profile:", cfg.get("gemma4_execution_profile"))
for key in ("moe_engine", "attention_engine", "attn_proj_engine", "dense_ffn_engine"):
    if cfg.get(key) != "htp":
        raise SystemExit(f"Expected {key}=htp; ask the pack provider")
print("Main files present. Also verify all sidecars from the provider's manifest.")
PY

du -sh "$NNTR_MODEL_PACK"

This is a presence check, not a validator for weight contents. Check any supplied checksums and sidecar manifest as well. The recommended chat files avoid template fallback and benchmark-only generation settings.

Copy the directory's contents, including sidecars, to the exact app directory:

adb shell mkdir -p /sdcard/Download/aistudio-mobile/models/gemma4-26b-a4b-htp-w4a32
adb push "$NNTR_MODEL_PACK/." /sdcard/Download/aistudio-mobile/models/gemma4-26b-a4b-htp-w4a32/
adb shell ls -lh /sdcard/Download/aistudio-mobile/models/gemma4-26b-a4b-htp-w4a32

Check that nntr_config.json is directly in that directory, not inside another nested pack directory. The multi-gigabyte transfer may take a while. Use /sdcard/Download so both the shell and the app can read the pack; /data/local/tmp is suitable for CLI binaries but is not an app-readable model location on a production phone.

7. Run Gemma4 from the command line

First run with the pack's default prompt

On the host:

cd "$NNTR_ROOT"
set -o pipefail
adb shell sh /data/local/tmp/Quick.AI/run_causallm.sh \
  /sdcard/Download/aistudio-mobile/models/gemma4-26b-a4b-htp-w4a32 \
  2>&1 | tee gemma4-cli.log

The wrapper sets the runtime library paths, enters /data/local/tmp/Quick.AI, and invokes nntr_causallm. With no second argument, the CLI uses chat_input through the pack's template if present, otherwise the raw sample_input. The supplied palette chat preset contains a summarization prompt.

A successful run produces an answer and timing output, including [e2e time]: ... ms and Max Resident Set Size: ... KB. Exact answer text and speed depend on the pack and device state. The first load can create tokenizer or weight-layout caches and take longer than later loads.

Give the CLI a short prompt

The interface is nntr_causallm <model_path> [input_prompt]. There are no --model, --prompt or --npu flags. The second argument is raw model input; the CLI does not apply a chat template to it.

To avoid host/ADB quoting mistakes, open a phone shell from the host:

adb shell

Then run this block inside the phone shell. The quoted text is one argument; its literal newlines and Gemma turn markers are intentional:

sh /data/local/tmp/Quick.AI/run_causallm.sh \
  /sdcard/Download/aistudio-mobile/models/gemma4-26b-a4b-htp-w4a32 \
  '<bos><|turn>user
Explain what a neural network is in two sentences.<turn|>
<|turn>model
<|channel>thought
<channel|>'
exit

For this preset, the empty thought channel requests a direct answer. Use the provider's matching template if your pack differs. Generation length is read from num_to_generate in nntr_config.json, not a CLI flag. The palette chat preset sets init_seq_len=2048, max_seq_len=2304 and num_to_generate=256: up to 2,048 prompt tokens with a 256-token answer budget. Supplied TL2 packs can use different settings. These defaults are separate from the fixed-output CLI configurations in the archived benchmark section.

Check NPU execution

A generated answer alone does not prove that the NPU ran. In this revision, a failed DSP open can log a warning and let the CLI fall back to the CPU. Capture device logs as well. In a second host terminal, select the same ANDROID_SERIAL if necessary and start logging before the next inference:

cd "$HOME/workspace/nntrainer-gemma4-pr4480"
adb logcat -v threadtime > gemma4-device.log

After the inference completes, press Ctrl+C in the logging terminal. Search both logs on the host:

grep -Ei 'HTP|nntr_hvx|FastRPC|adsprpc|cdsprpc|falling back|CPU fallback' \
  gemma4-cli.log gemma4-device.log

Treat nntr_hvx_open failed, HTP backend disabled, falling back to CPU, or operation-level CPU fallback messages as a failed NPU check. Resolve missing skel/library or device-session errors before comparing performance. HTP arena mapping and graph activity are useful supporting evidence, but an isolated HTP label is not proof of successful offload. Some CPU work is intentional; for example, the palette pack's tied language-model head uses the CPU.

For a stronger check using the app's C API, run this from the host after the CLI finishes:

adb shell 'sh /data/local/tmp/Quick.AI/run_test.sh \
  gemma4-26b-a4b-htp "Explain neural networks in two sentences." \
  true W4A32 1 /sdcard/Download/aistudio-mobile/models'

Here true enables chat-template application to the plain-text prompt. The latest run_test.sh sets QUICKAI_NATIVE_LIB_DIR and ADSP_LIBRARY_PATH to /data/local/tmp/Quick.AI with no trailing colon. It also sets the native library path and the configured thread count. After updating the source, repeat the build/install step to replace the old wrapper on the phone.

For the optional lifecycle test, run:

adb shell 'QDA_HTP_LIFECYCLE=1 sh /data/local/tmp/Quick.AI/run_test.sh \
  gemma4-26b-a4b-htp "Explain neural networks in two sentences." \
  true W4A32 1 /sdcard/Download/aistudio-mobile/models'

It checks repeated generation, cancellation, unload/reload and invalid packs. Successful checks print [HTP-API-TEST] PASS ...; retain logs and check the exit status. Unload the model in the app before running CLI/API tests.

8. Build and install the Quick.AI app

The instructions follow the updated app at the source revision above. The model-selection and chat examples are real Quick.AI 2.0 captures from November 4, 2026 (Galaxy S26 Ultra SM-S948N / SM-S948U, Android 16, 4 KB pages). The Metrics image was refreshed on November 5 on SM-S948U and shows the benchmark setup. The installed APKs' source commits were not established; the captures illustrate the controls, while the pinned source defines their behaviour. Click an image to open its full-resolution capture.

Build and install the APK

On the host, reuse the same environment and source revision:

cd "$NNTR_ROOT/Applications/CausalLM"
set -o pipefail
./build_android.sh --htp --cache --app 2>&1 | tee "$NNTR_ROOT/gemma4-app-build.log"

This stages the native libraries, builds the library AAR and sample APK, and runs verify_native_package.py. That verification checks required libraries, the unmodified v81 DSP image and native library dependencies. It also rejects unwanted QNN or vendor libcdsprpc.so libraries in the HTP package.

Token counts and measurement boundaries

  • 128 output tokens = one token selected during prefill + 127 decode steps. For this CLI, num_to_generate=127 produces that total; its generation: log line therefore says 127 tokens. Native token traces confirmed all 128 output IDs and the exact input IDs in every run.
  • Prefill is the CLI's input-processing throughput. Decode is 127 / generation_seconds, including the first decode step. It is not calculated from the reciprocal of the steady-token median.
  • TTFT comes from the CLI's [PERF-SPLIT] ttft_ms: inference start to first token delivery. Model loading and process startup are excluded, so this is not app launch-to-answer latency.
  • Peak memory is the runtime's sampled RssAnon + accelerator peak, converted from KiB to GiB. It excludes file-backed page cache and is not total phone RAM usage or the weight-file storage requirement.

Only isolated benchmark copies of the configuration were changed: the prompt, output limit, greedy setting, trace path and EOS suppression (bad_word_ids=[1,50,106]). EOS suppression keeps all outputs at the requested length; normal chat should retain the provider's stopping settings. The deployed pack and app configuration were left unchanged.

App reports pack not found Check base path, exact directory name, all-files permission and accidental extra nesting after adb push.

Reading the LFM2 measurements

  • Output count: one token selected during prefill plus 127 decode steps gives 128 total output IDs. The CLI's generation: line reports 127 tokens.
  • Speed: Prefill is input tokens divided by prefill time; Decode is 127 / generation_seconds, including the first decode step.
  • TTFT: native [PERF-SPLIT] ttft_ms, excluding process startup and model loading. It is not app launch-to-answer latency.
  • Peak memory: sampled RssAnon + accelerator, converted from KiB to GiB. File-backed page cache is excluded; this is not total phone RAM usage or weight-file storage size.

The workload measures throughput on synthetic report prompts. It does not measure model accuracy or sustained performance on a hot phone. Gemma4 and LFM2 differ in architecture, active parameter count, tokenization, KV format and execution preset, even though the measurement procedure is aligned.
