Hexagon NPU에서 Gemma4-MoE 실행하기

이 가이드는 Linux PC와 Android 휴대전화에서 도구를 준비하고, 명령줄 또는 Quick.AI Android 앱으로 Gemma4 26B-A4B의 첫 응답을 생성하는 과정을 설명합니다. 툴체인 설치, nntrainer 빌드, 런타임 설치, 모델 팩 복사, 실제 NPU 실행 여부 확인까지 순서대로 진행합니다.

기준 소스: PR #4480의 커밋 67d2903a279a3f5604074f001bbf8f814dfb9f82. 2026-11-05에 내용을 검토했습니다. 아래 명령은 SDK와 HexKL 6.4.0.1 조합, 업데이트된 Metrics 벤치마크, 2,304개 위치의 Gemma4 채팅 프리셋이 포함된 이 리비전을 기준으로 합니다. 화면 캡처와 벤치마크의 날짜는 아래에 따로 기록했습니다. 다른 체크아웃에서는 명령이나 기능이 달라질 수 있습니다.

별도로 제공되는 실행 가능한 Gemma4 HTP 모델 팩이 필요합니다. 이 저장소와 APK에는 가중치가 포함되어 있지 않습니다. 이 PR에는 제공용 모델 팩의 공개 다운로드 URL이 안내되어 있지 않습니다. 추론을 시작하기 전에 모델 제공자로부터 팩과 그에 맞는 설정을 받아야 합니다. 일반 Hugging Face 체크포인트를 다운로드하는 것만으로 이 단계를 대체할 수는 없습니다.

bash 코드 블록은 adb로 시작하는 명령을 포함해 모두 Linux PC의 Bash에서 실행합니다. sh 블록은 휴대전화의 adb shell 안에서 실행합니다. 예제 경로는 실제 절대 경로로 바꾸세요. 내보낸 환경 변수가 유지되도록 같은 호스트 터미널에서 계속 진행하세요. 오류가 발생하면 해결한 다음 단계로 넘어가세요. 명령, 옵션, 로그, 앱의 UI 이름은 실제 화면과 대조할 수 있도록 원문을 유지합니다.

각 구성 요소의 역할

  • Android NDK: 휴대전화 CPU에서 실행할 ARM64 코드를 컴파일합니다.
  • Hexagon SDK와 Tools: DSP/NPU 코드를 컴파일하고 FastRPC를 통해 연결합니다.
  • HexKL: nntrainer에서 HTP라고 부르는 Hexagon 백엔드에 커널을 제공합니다.
  • libnntr_hvx_skel.so: 이 PR에서 빌드하는 nntrainer의 DSP 프로그램입니다. 같은 빌드의 ARM 측 라이브러리와 짝이 맞아야 합니다.
  • QuickDotAI / Quick.AI: 각각 재사용 가능한 Android 라이브러리(AAR)와 예제 앱(APK)입니다.

이 가이드는 --htp를 사용하며 QNN SDK가 필요하지 않습니다. 최신 스크립트는 --qnn --htp 통합 패키지도 지원하지만, 이 경우 QNN 의존성도 추가로 필요합니다. OpenCL은 기본으로 켜져 있습니다. OpenCL/GPU 백엔드를 제외하려면 빌드·설치 명령에 --disable-opencl을 일관되게 사용하세요.

java -version 결과가 Java 17이어야 합니다. 위 명령은 호스트 빌드 도구를 설치하며, Android용 컴파일러는 NDK가 제공합니다. 아래의 Android 빌드 대신 호스트용 nntrainer 패키지를 설치하면 안 됩니다.

공식 rustup 설치 프로그램으로 Rust를 설치합니다. 설치 방식이 표시되면 기본 설치를 선택하세요.

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/nntr-rustup-init.sh
sh /tmp/nntr-rustup-init.sh
source "$HOME/.cargo/env"
rustup target add aarch64-linux-android
rustc --version
cargo --version

Rust는 저장소의 토크나이저 라이브러리를 빌드하는 데 사용합니다. 빌드 스크립트가 이 라이브러리의 Android C/C++ 컴파일러 설정을 처리하므로 별도의 토크나이저 체크아웃이나 cargo-ndk 설치는 필요하지 않습니다.

Android SDK와 NDK

Android Studio 다운로드 페이지에서 Command line tools only → Linux를 다운로드합니다. 임시 디렉터리에 압축을 풀고, Google의 SDK Manager 안내에 따라 SDK Manager가 $HOME/Android/Sdk/cmdline-tools/latest/bin/sdkmanager에 위치하도록 배치합니다. 아래 예제의 압축 파일 이름을 실제 다운로드한 이름으로 바꾸세요.

export ANDROID_HOME="$HOME/Android/Sdk"
export NNTR_ANDROID_TOOLS_ZIP="$HOME/Downloads/commandlinetools-linux-REPLACE_ME_latest.zip"
NNTR_ANDROID_TOOLS_TMP=$(mktemp -d)
unzip "$NNTR_ANDROID_TOOLS_ZIP" -d "$NNTR_ANDROID_TOOLS_TMP"
mkdir -p "$ANDROID_HOME/cmdline-tools/latest"
cp -a "$NNTR_ANDROID_TOOLS_TMP/cmdline-tools/." "$ANDROID_HOME/cmdline-tools/latest/"
export PATH="$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH"
sdkmanager --version

Android Studio에서 SDK를 이미 설치했다면 해당 SDK 경로를 사용하고, SDK Manager에서 Android SDK Command-line Tools를 설치하세요. ANDROID_HOME과 기존 ANDROID_SDK_ROOT가 있다면 둘 다 같은 디렉터리를 가리키게 합니다. 여기서는 command-line tools 패키지에 포함된 SDK Manager를 사용합니다.

지정된 버전의 패키지를 설치하고 Android 라이선스를 검토한 뒤 동의합니다.

sdkmanager --sdk_root="$ANDROID_HOME" --licenses
sdkmanager --sdk_root="$ANDROID_HOME" \
  "platform-tools" "platforms;android-36" "build-tools;36.0.0" \
  "cmake;3.22.1" "ndk;30.0.16248370"

export ANDROID_NDK="$ANDROID_HOME/ndk/30.0.16248370"
cat "$ANDROID_NDK/source.properties"
"$ANDROID_NDK/toolchains/llvm/prebuilt/linux-x86_64/bin/clang" --version
adb version

NDK 리비전은 NDK r30에 해당하는 30.0.16248370이어야 합니다. 별도의 android-ndk-r30-linux.zip을 사용한다면 압축을 풀고 생성된 android-ndk-r30 디렉터리를 ANDROID_NDK로 지정하세요. 앱 빌드는 네이티브 빌드와 같은 NDK 경로를 사용합니다. 저장소가 Gradle wrapper를 제공하므로 시스템 Gradle을 따로 설치할 필요는 없습니다.

3. Hexagon SDK와 HexKL beta2 설치

Qualcomm 패키지 받기

공식 Qualcomm Software Center의 Hexagon SDK 카탈로그와 Qualcomm Package Manager를 이용합니다. 로그인이 필요하면 Qualcomm 계정으로 로그인하세요. Linux용 Hexagon SDK 6.4.0.1을 선택하고 Hexagon Tools 19.0.04 구성 요소를 설치합니다. 설치 프로그램에 표시된 설치 경로를 사용하세요. 아래 예제에서는 $HOME/Qualcomm/Hexagon_SDK/6.4.0.1을 사용합니다.

포털에서 Linux용 Package Manager 앱을 요구한다면 Debian 패키지를 내려받아 설치한 다음 앱을 열고 로그인합니다.

# Replace the filename with the package you actually downloaded.
sudo apt install "$HOME/Downloads/QualcommPackageManager3.3.0.133.0.Linux-x86.deb"

Qualcomm 카탈로그에서 **Hexagon Kernel Library(HexKL)**도 찾아 1.0 beta2를 선택합니다. HexKL은 SDK와 별도로 배포됩니다. Qualcomm AI Stack 카탈로그에서도 해당 패키지를 찾을 수 있습니다. 포털 화면과 사용할 수 있는 버전은 계정에 따라 달라집니다. 필요한 버전이 없다면 Qualcomm이나 패키지 제공자에게 접근 권한을 요청하세요. 확인 없이 다른 릴리스로 대체하지 마세요. 이 가이드는 익명으로 접근할 수 있는 패키지 다운로드 URL을 전제로 하지 않습니다.

제공받은 beta2 ZIP을 풉니다. 아래 예제는 최상위 디렉터리가 hexkl_addon인 hexkl-1.0-beta.2.zip을 사용합니다.

mkdir -p "$HOME/Qualcomm/HexKL/1.0-beta2"
unzip "$HOME/Downloads/hexkl-1.0-beta.2.zip" -d "$HOME/Qualcomm/HexKL/1.0-beta2"
export HEXKL_ROOT="$HOME/Qualcomm/HexKL/1.0-beta2/hexkl_addon"
head -n 8 "$HEXKL_ROOT/README.md"

README에 1.0 Beta.2가 표시되어야 합니다. 다운로드 파일이 한 번 더 압축되어 있다면 바깥 압축부터 풀고, 실제 include/와 lib/가 들어 있는 디렉터리를 HEXKL_ROOT로 지정하세요.

환경 변수 설정

호스트 PC에서 설치된 SDK의 환경 스크립트를 먼저 불러온 뒤, Android와 HexKL 경로를 명시적으로 설정합니다.

source "$HOME/Qualcomm/Hexagon_SDK/6.4.0.1/setup_sdk_env.source"

export HEXKL_ROOT="$HOME/Qualcomm/HexKL/1.0-beta2/hexkl_addon"
export HEXKL_SDK_VER=6.4.0.1
export HEXKL_TOOLS_VARIANT=toolv19
export HEXKL_ARCH=armv8_android26
export HEX_ARCH=v81
export ANDROID_HOME="$HOME/Android/Sdk"
export ANDROID_NDK="$ANDROID_HOME/ndk/30.0.16248370"
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
export PATH="$JAVA_HOME/bin:$HOME/.cargo/bin:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/platform-tools:$PATH"

setup_sdk_env.source가 HEXAGON_SDK_ROOT와 DEFAULT_HEXAGON_TOOLS_ROOT를 설정합니다. SDK를 다른 곳에 설치했다면 source 경로를 바꾸세요. 새 터미널을 열 때마다 이 블록을 다시 실행하거나, 소스 체크아웃 밖의 셸 파일에 저장해 불러오세요.

Hexagon SDK와 HexKL 라이브러리 선택에 모두 6.4.0.1을 사용하세요. HexKL의 lib/<version>은 라이브러리가 대상으로 하는 SDK 버전입니다. HEXKL_SDK_VER=6.4.0.1로 lib/6.4.0.1을 선택합니다. 그 아래 armv8_android26/libsdkl.so는 Android 런타임으로 배포되고, hexagon_toolv19_v81/libhexkl_micro.a는 DSP 빌드에 링크됩니다. 두 빌드 스크립트의 기본값도 이 버전입니다. DSP 스크립트는 더 이상 가장 최신 디렉터리를 자동으로 고르지 않습니다. 해당 디렉터리가 실제로 있는지 확인하고, 경로 검사만 통과시키려고 다른 버전의 디렉터리 이름을 바꾸지 마세요.

빌드 전에 경로를 확인합니다.

printf 'SDK: %s\nTools: %s\nHexKL: %s\n' \
  "$HEXAGON_SDK_ROOT" "$DEFAULT_HEXAGON_TOOLS_ROOT" "$HEXKL_ROOT"

ls "$HEXAGON_SDK_ROOT/setup_sdk_env.source" \
   "$HEXAGON_SDK_ROOT/rtos/qurt/computev81/include/qurt" \
   "$HEXKL_ROOT/include/hexkl_micro.h" \
   "$HEXKL_ROOT/lib/$HEXKL_SDK_VER/armv8_android26/libsdkl.so" \
   "$HEXKL_ROOT/lib/$HEXKL_SDK_VER/hexagon_toolv19_v81/libhexkl_micro.a"

"$DEFAULT_HEXAGON_TOOLS_ROOT/Tools/bin/hexagon-clang" --version

모든 경로가 존재해야 하며 컴파일러는 Tools 19.0.04에 포함된 것이어야 합니다. DEFAULT_HEXAGON_TOOLS_ROOT는 Tools/bin이 아니라 Tools/의 상위 디렉터리를 가리킵니다. HexKL은 미리 빌드된 라이브러리를 제공하므로 nntrainer를 위해 모든 HexKL 예제를 빌드할 필요는 없습니다. 일반 libhexkl_skel.so는 nntrainer의 libnntr_hvx_skel.so를 대체할 수 없습니다.

출력 해시가 가이드 상단의 기준 소스와 일치해야 합니다. PR이 이후 변경되더라도 이 절차는 지정된 리비전을 사용합니다. 서브모듈은 빌드에 필요하며, 초기화하는 것은 벤더 소스를 수정하는 것과 다릅니다. 첫 토크나이저 및 Gradle 빌드에서도 다운로드가 발생하므로 인터넷 연결을 유지하세요.

ADB 연결 승인

휴대전화에서 **빌드 번호(Build number)**를 일곱 번 눌러 개발자 옵션을 켭니다. 삼성 기기는 설정 → 휴대전화 정보 → 소프트웨어 정보에 있습니다. 개발자 옵션에서 USB 디버깅을 켜고 데이터 전송이 가능한 USB 케이블을 연결하세요. 잠금을 해제한 휴대전화에서 디버깅 허용 요청을 승인합니다.

호스트 PC에서 실행합니다.

adb devices -l

기기가 unauthorized나 offline이 아닌 device 상태여야 합니다. 여러 기기나 에뮬레이터가 연결되어 있다면 출력에 표시된 시리얼을 지정합니다.

# Replace this value with the serial from adb devices -l.
export ANDROID_SERIAL=REPLACE_WITH_DEVICE_SERIAL
adb get-state
adb shell getprop ro.product.model
adb shell getprop ro.soc.model
adb shell getprop ro.build.version.release
adb shell getconf PAGE_SIZE
adb shell df -h /sdcard

기기가 하나뿐이면 ANDROID_SERIAL을 설정하지 않아도 됩니다. 기준 환경은 S26 Ultra / SM8850, Android 16, 페이지 크기 4096입니다. 빌드와 런타임 호환성은 펌웨어 및 FastRPC 지원에도 영향을 받으므로 이 속성만으로 NPU 실행을 입증할 수는 없습니다. 이 절차에서 adb root는 필요하지 않습니다.

5. 네이티브 런타임 빌드 및 설치

--cache는 호환되는 엔진 빌드를 재사용하지만 나머지 빌드 단계는 수행합니다. --install은 실행 파일과 런타임 라이브러리를 /data/local/tmp/Quick.AI에 배포하고, 이 경로에서 스크립트가 관리하는 런타임 파일을 교체합니다. run_causallm.sh와 run_test.sh 실행 래퍼도 생성합니다. 모델 팩은 복사하지 않습니다.

런타임에는 HexKL의 libsdkl.so와 NDK의 libc++_shared.so가 포함됩니다. libcdsprpc.so는 휴대전화의 vendor 파티션에서 제공합니다. ARM 라이브러리, stub, DSP 이미지는 함께 빌드하고 배포하세요. 새 빌드에 오래된 DSP 이미지만 복사하면 서로 사용하는 프로토콜이 맞지 않을 수 있습니다.

--clean은 선택한 CausalLM 네이티브 빌드 디렉터리를 다시 만듭니다. 모든 엔진 및 Gradle 캐시까지 지운다는 의미는 아닙니다. HTP의 기본 CPU 스레드 수는 8이며 첫 실행에서는 그대로 사용하세요.

최신 스크립트의 --stage는 공개 네이티브 파일을 builddir_app_stage/public/htp/에 모으고 옆에 .manifest.json 보고서를 만듭니다. --stage=DIR로 지정한 전용 디렉터리는 실행할 때마다 다시 생성됩니다. 라이브러리를 다른 앱에 통합할 때 사용하는 옵션이며, 일반 앱 빌드는 자체적으로 파일을 준비합니다. --cache는 OpenCL 설정도 확인하여 호환되는 엔진만 재사용합니다.

앱은 휴대전화에 다음 디렉터리 구조가 있다고 가정합니다.

config.json에는 텍스트 모델 설정이 최상위에 있어야 합니다. text_config만을 담은 래퍼 구조이면 안 됩니다. 제공자의 nntr_config.json에서 htp_fused / htp_fused_v1, 각 연산의 실행 엔진, 실제 가중치 형식을 지정합니다.

이 PR에는 두 계열의 Gemma4 팩이 있습니다.

팩 Expert 형식 Projection / head
제공되는 팔레트 팩 QS2CX_WH QS4CX projection, CPU에서 실행하는 임베딩 공유 Q4_0 head
네이티브 삼진 팩 TL2CX_WH, 일부 affine expert 레이어가 섞일 수 있음 QS4CX_WH_AFFINE projection과 임베딩을 공유하지 않는 HTP head

앱의 W4A32는 카탈로그 선택값이며 모든 텐서의 가중치가 4비트라는 뜻은 아닙니다. 이 표시에 맞추려고 dtype 이름을 변경하지 마세요. 특히 TL2 팩의 nntr_config.json을 Applications/CausalLM/res/gemma4/htp_chat/의 팔레트 프리셋으로 덮어쓰면 안 됩니다. 팔레트 팩에 채팅 프리셋이 필요하다면 설정 파일을 교체하기 전에 제공자에게 가중치와 프리셋의 호환 여부를 확인하세요. 형식과 선택적 보조 파일(sidecar)은 PR의 모델 팩 규약에 자세히 설명되어 있습니다.

이전 팩을 이 리비전에서 사용하려면 삭제된 옵션의 설정 이행 안내를 따르세요. 삭제된 중첩 htp / moe 키는 로드 시 거부됩니다. 호환되는 팩 설정의 복사본에서 나열된 키를 제거하고, TL2 설정을 팔레트 프리셋으로 바꾸지 마세요. 체크포인트에 같은 회전이 필요하다면 삭제된 moe.hadamard=both_scalar 값은 both로 변경합니다.

NPU 실행 확인

답변이 생성되었다는 사실만으로 NPU가 실행되었다고 볼 수는 없습니다. 이 리비전은 DSP 열기에 실패하면 경고를 남기고 CLI가 CPU로 전환될 수 있습니다. 기기 로그도 함께 수집하세요. 두 번째 호스트 터미널에서 필요하면 같은 ANDROID_SERIAL을 지정하고 다음 추론을 시작하기 전에 로그 수집을 시작합니다.

adb logcat -v threadtime > gemma4-device.log

추론이 끝나면 로그를 수집하는 터미널에서 Ctrl+C를 누릅니다. 호스트에서 두 로그를 검색합니다.

grep -Ei 'HTP|nntr_hvx|FastRPC|adsprpc|cdsprpc|falling back|CPU fallback' \
  gemma4-cli.log gemma4-device.log

nntr_hvx_open failed, HTP backend disabled, falling back to CPU, 또는 연산별 CPU fallback이 보이면 NPU 확인이 실패한 것으로 판단하세요. 성능을 비교하기 전에 skel/라이브러리 누락이나 기기 세션 오류를 해결해야 합니다. HTP arena 매핑과 그래프 실행 로그는 참고가 되지만 HTP라는 표시만으로 offload 성공을 입증할 수는 없습니다. 일부 CPU 연산은 의도된 동작입니다. 예를 들어 팔레트 팩의 임베딩 공유 언어 모델 head는 CPU를 사용합니다.

앱과 같은 C API를 통해 추가로 확인하려면 CLI가 끝난 뒤 호스트 PC에서 실행합니다.

여기서 true는 일반 텍스트 프롬프트에 채팅 템플릿을 적용합니다. 최신 run_test.sh는 QUICKAI_NATIVE_LIB_DIR와 ADSP_LIBRARY_PATH를 끝에 콜론 없이 /data/local/tmp/Quick.AI로 설정합니다. 네이티브 라이브러리 경로와 스레드 수도 설정합니다. 소스를 업데이트한 뒤에는 빌드·설치 단계를 다시 수행하여 기기에 남아 있는 이전 래퍼도 교체하세요.

토큰 수와 지표의 집계 범위

  • 출력 128토큰 = 프리필에서 선택한 첫 토큰 1개 + 디코딩 127단계입니다. 이 CLI에서는 num_to_generate=127로 설정해야 전체 128개가 생성되므로, generation: 로그에는 127 tokens라고 나옵니다. 매 실행 네이티브 토큰 트레이스에서 출력 ID 128개와 정확한 입력 ID를 모두 확인했습니다.
  • Prefill은 CLI가 보고한 입력 처리 속도입니다. Decode는 127 / generation_seconds로 계산하며 첫 디코딩 단계도 포함합니다. Steady decode 중앙값의 역수로 계산한 값과는 다릅니다.
  • TTFT는 CLI의 [PERF-SPLIT] ttft_ms, 즉 추론 시작부터 첫 토큰 전달까지의 시간입니다. 모델 로드와 프로세스 시작 시간은 제외하므로 앱 실행부터 답변까지의 전체 지연 시간으로 해석하면 안 됩니다.
  • 최대 메모리는 런타임이 샘플링한 RssAnon + accelerator의 최댓값을 KiB에서 GiB로 환산한 값입니다. 파일 페이지 캐시는 제외하며, 휴대전화 전체 RAM 사용량이나 가중치 파일에 필요한 저장 공간과는 다릅니다.

벤치마크 전용으로 복사한 설정에서만 프롬프트, 출력 제한, greedy 설정, 트레이스 경로, EOS 억제(bad_word_ids=[1,50,106])를 적용했습니다. EOS 억제는 출력 길이를 128개로 고정하기 위한 조건이며, 일반 채팅은 제공자의 종료 설정을 유지하세요. 배포 모델 팩과 앱 설정은 변경하지 않았습니다.

원본 기록과 재현 방법

요약 JSON, 개별 실행 CSV, 전체 측정 기록 ZIP을 내려받을 수 있습니다. ZIP에는 CLI 원본 로그, 실제 프롬프트와 예상 입력 토큰 ID, 네이티브 토큰 트레이스, 실행별 설정, 온도 기록, 바이너리·가중치 체크섬과 측정 스크립트가 들어 있습니다. 모델 가중치와 런타임 바이너리는 포함하지 않습니다.

LFM2 결과 해석

  • 출력 수: 프리필에서 선택한 첫 토큰 1개와 디코딩 127단계를 합쳐 총 128개입니다. CLI의 generation: 로그에는 127토큰으로 표시됩니다.
  • 속도: Prefill은 입력 토큰 수를 프리필 시간으로 나눈 값이고, Decode는 첫 디코딩 단계를 포함한 127 / generation_seconds입니다.
  • TTFT: 네이티브 [PERF-SPLIT] ttft_ms이며 프로세스 시작과 모델 로드 시간은 제외합니다. 앱 실행부터 답변까지의 전체 지연 시간이 아닙니다.
  • 최대 메모리: 샘플링한 RssAnon + accelerator를 KiB에서 GiB로 환산했습니다. 파일 페이지 캐시는 제외하며, 휴대전화 전체 RAM 사용량이나 가중치 저장 공간과는 다릅니다.

합성 보고서 프롬프트의 처리량 측정이며 모델 정확도나 뜨거워진 기기의 장시간 지속 성능을 평가한 결과는 아닙니다. 측정 절차를 맞췄더라도 Gemma4와 LFM2는 모델 구조, 활성 파라미터 수, 토크나이저, KV 형식과 실행 프리셋이 다릅니다.
