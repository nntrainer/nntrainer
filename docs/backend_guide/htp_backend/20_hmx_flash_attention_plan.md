# HMX flash attention for the HTP backend — analysis and plan

Status: 2026-09-22. Branch: `htp/quant-dequant-hvx-opt`.
**Verified on device** (SM8850 / Hexagon v81, SDK 6.4.0.2, HexKL addon
`lib/6.4.0.1`): `unittest_hvx_attn_f16` 25/25, `unittest_hvx_mm_u8i4` 14/14,
host planner and registry tests 13/13. All seven Phase 0 layout probes
read 1 on this part (AH == WH for fp16, hand tilers == HexKL tilers, diag
tile, fused f32 -> AH). SNR against the f32 host reference: HMX prefill
62-67 dB, HVX decode 63-78 dB, resident tiles bit-identical to the raw
path. Timings (us, one FastRPC call, DSP-side timers): prefill
128x1024, 16/4 heads, hd 128: qk 229, softmax 428, pv 272, dma 632,
store 653 over 256 blocks -- and tile 91062, i.e. the raw-row path is
entirely the HVX tile build, which the resident path removes (tile 0,
same qk/pv). Decode 1x1024 (16/4 x 128) 811 us, 1x4096 3274 us.
Two device-only bugs were found and fixed on the way, both worth
knowing about when writing more HVX fp16 code here (see §5).

Phases 0, 1 and 2 are code-complete and build-verified (hexagon-clang v81
`-Wall -Werror` for the DSP skel; NDK aarch64 for the gtest; host planner
tests pass). Phase 2 delivered: softmax and K^T/V tile builds across the
worker pool, attention sink (matches NEON `softmax_row_with_sink_inplace`:
max seeded with the sink, sum with exp(sink-max)) and logit softcap
(tanh via exp2 + f32 reciprocal), and the pure-HVX decode kernel
`hvx_attn_decode_f16` with its own IDL entry and gtests. Phase 3 delivered:
`hvx_worker_pool_submit/wait` and the pipelined kernel (HVX softmax of
block k overlaps the DMA landing, tile build and HMX Q.K^T of block k+1;
S double-buffered), the Br/Bc chooser (`hexkl_attn_f16_choose_tiling`,
host-tested), and the resident KV tile registry `hexkl_kv_tiles_f16`
("NativeKV": `kv_register/append/release_f16`, `attn_f16_prefill_resident`;
blocks land as one DMA of 2 KiB tile rows with no tile phase; the device
test requires bit-identity with the raw path). Phase 4 delivered (4a-4c):
the `ComputeOps::supports_sdpa_fp16_kvcache` / `sdpa_fp16_kvcache` pair,
`HtpBackend` re-pointed from the SDKL macro API to the micro-API FastRPC
session (stub generated by `generate_stub.sh`, libcdsprpc wired into the
Android build), `HtpComputeOps` routing the op to `attn_f16_decode`
(n_q < 5, hd <= 128) or `attn_f16_prefill`, and `MHACoreLayer` consulting
its context's ComputeOps before steps 2-4 with the CPU path as fallback.
Phase 4d delivered: the KV cache in rpcmem. `ComputeOps::alloc_shared /
free_shared` (HTP: `rpcmem_alloc`, a dma-buf the rpcmem library registers
with FastRPC), `KVCacheManager::setSharedAllocator` wrapping each slab
without a copy, and `CausalLM` routing the cache there when
`"attention_engine"` in nntr_config.json names an engine -- the same knob
that puts the `mha_core` layers on that engine. FastRPC then maps the used
cache range into the DSP and cache-maintains it instead of copying it per
call. Measured on device (host-side call time, median of 8, same bytes
out): decode 1x4096 (16/4 x 128, 8 MiB of cache) 8203 -> 4226 us against
3274 us of DSP time, i.e. the transport overhead fell from ~4.9 ms to
~0.95 ms; decode 1x1024 1246 -> 1051 us; prefill is compute-bound and
moves by 0.6-3.4 ms. Not done: the E2E CausalLM benchmark (needs an
Android build of the app with `-Denable-htp` and a model on the device).
On a new part, run
`test/htp/run_u8i4_layer_on_device.sh` first: its summary prints the
`ATTN_F16_FIELD probe=...` flags, and a 0 there means a layout assumption
in §3.4 is wrong on that part and the kernel's numbers are void until it
is fixed. Build the skel with `HEX_ARCH=v81` for SM8850.

Goal: an attention layer that runs inside nntrainer's HTP context, on HMX like
the existing u8i4/u8i8 layers, optimized to the level of llama.cpp's
`ggml-hexagon` flash attention.

## 1. Where things stand

### 1.1 This branch
No attention code. What exists and is reusable, all under
`nntrainer/tensor/htp_backend/` and `test/htp/`:

- Session (`nntr_hvx_open`): `hexkl_micro_hw_init`, HMX lock, VTCM arena,
  **int32** accumulator config only, `hvx_worker_pool` (fork/join, one job).
- `hexkl_dma_ring`: dmlink-chained 2D user DMA, DDR<->VTCM, drain.
- `hvx_quant_u8` / `hvx_dequant_i32`: parallelized across the pool.
- FastRPC IDL (`nntr_hvx.idl`) + DSP skel build (`build.sh`) + ARM gtest
  pattern with host references and SNR gates (`unittest_hvx_mm_u8i4.cpp`).
- Tooling verified: SDK 6.4.0.2 + HexKL addon with the full f16 micro API
  (`hmx_mm_f16`, `acc_read_f16`, `rm_to_ah_f16`, `rm_to_wh_f16`,
  `copy_psubmatrix_to_f16_weight`, `setup_acc_read_f16`).

### 1.2 Prior attention work on other branches (not on this one)
Two disjoint families, from `seunghui/htp/rope-u8-qnn-parity` and
`seunghui/claude/hexkl-mha-hmx-optimization-6ycsx0`:

| | u8i4/u8i8 fused SDPA | fp16 Q.K^T / P.V bench |
|---|---|---|
| state | production-tree code, +4.1k lines | standalone DSP `main()`, unwired |
| softmax | blocked (full row), not online | n/a (matmuls only) |
| S/P/O | round-trip **DDR** | VTCM |
| measured | int32 acc readout = 96% decode / 75% prefill; ~4x behind QNN | prefill-128 Q.K^T 553 us/layer vs 24-36 ms CPU (43-65x); P.V 371 us (43-55x); decode 2.4-3.4x |
| accuracy | never measured | fp16 acc, K=1024: max rel err 3e-4 |

Facts from that work this plan depends on:
- `hexkl_micro_hw_init` permanently breaks the SDKL macro API in-process ->
  everything stays on the micro API (already true here).
- HexKL *extraction* helpers (`copy_submatrix_to_f16`, `rm_to_wh_f16`) read
  DDR fast but are ~400x slower reading VTCM. Fixed-tile `rm_to_ah_f16` /
  `ah_to_rm_f16` are fast from either.
- DMA bandwidth is set by row size: 64 B rows 8 GB/s, 2 KiB 42, 64 KiB 55.
  A per-kv-head slice of the cache is one strided 2D descriptor.
- `hvx_exp_sf` is undefined above +88.7: masked lanes must be excluded
  from the row **max**, not just the sum.
- VTCM is 8 MiB. Pool-parallel HVX work over VTCM showed +30% bank
  contention.
- f16 AH and WH per-tile layouts are the same 2-row interleave (tutorial,
  v75; llama.cpp relies on it on v79 too).

### 1.3 CPU contract the kernel must match (`Applications/CausalLM/layers/mha_core.cpp`)
- Q `(B,1,S,n_head_Q*hd)` f32, **post-RoPE**. KV cache
  `(B,1,max_ts,n_head_KV*hd)`, **fp16 in a u16 container**, row-major, K
  stored post-RoPE, V raw. Yarn scaling is folded into RoPE tables, not the
  QK scale.
- `scale = 1/sqrt(hd)` applied in the QK kernel. GQA `G = n_head_Q/n_head_KV`.
- Causality is expressed by **not computing** masked entries (no mask
  tensor). Logits are triangular-packed, head-minor. Optional: sliding
  window, logit softcap `tanh(x/c)*c`, attention sink (extra per-head logit
  in the denominator).
- Output `(B,1,S,n_head_Q*hd)`, row `q`: `out[(n*G+g)*hd + d]`.
- `MHACoreLayer` never consults `ComputeOps`; `get_htp_ops()` returns
  `get_cpu_ops()`. The seam has to be created.

### 1.4 The bar: llama.cpp `ggml-hexagon/htp/flash-attn-ops.c`
- FA-2 online softmax. Running `m`, `l` in fp32 VTCM vectors. The
  rescale `exp2(m_prev - m_curr)` is scattered onto the diagonal of 32x32
  f16 tiles and applied **on HMX**: `O = D.O_prev + P.V` as one accumulation,
  final `O = diag(1/l).O`. O never touches HVX until the store.
- `scale*log2e` folded into the HMX output-scale register; softmax is
  base-2, `exp2` in f16 (input clamped at -24), row sums in qf32.
- GQA free: rows of the tile dimension are `q*G + h`; one Q.K^T per KV head.
- K transposed during DDR->VTCM tile staging (vscatter); V tiled
  column-tile-major; O kept column-tile-major so it feeds back as the
  weight of `D.O_prev` with no relayout.
- K/V streamed by DMA with depth-2 prefetch; HMX on a dedicated thread
  behind a 16-deep queue; HVX softmax of block i overlaps HMX Q.K^T of
  block i+1 and O-update of i-1. Pipeline needs >= 3 KV blocks.
- Bc multiple of 64, `g_br = align_up(G*Br, 32)`; chosen by a host-side
  cost search (`800 + kv_blocks*(200 + 600*vecs_per_thread)` per Q block).
- **Decode (`n_tokens < 5`, hd <= 128) goes to pure HVX**, one (token, head)
  per work item, fp32 accumulator. HMX only for prefill or big heads.
- Device numbers (8 Elite/v79, whole model): pp128 415-494 tok/s on 0.6-1B.

## 2. Decisions

1. **Precision: fp16 HMX, fp16 KV.** Matches nntrainer's existing cache,
   llama.cpp's default, and the only path with measured accuracy. u8 KV
   attention has no accuracy data and QNN ships int8 KV, not int4.
2. **Algorithm: FA-2 online softmax with the HMX diagonal rescale**, as
   llama.cpp. The prior branch's "one accumulator, can't rescale" reasoning
   only holds if O stays in the HMX accumulator across blocks; reading O out
   per block and folding the rescale into the next HMX pass is the fix.
3. **Formulation `S = Q.K^T`** (Q activation, K^T weight), not the prior
   `S^T = K.Q^T`: keeps softmax reductions along HVX rows and P directly
   usable as the P.V activation.
4. **Scale handling.** HexKL does not expose the HMX output-scale register
   (only `setup_acc_read_f16` with scale 1). Fold `scale*log2e` into the
   f32->f16 conversion of Q during AH prep. Free, no accuracy concern.
5. **Causal mask by geometry, not by tensor.** Per (q_block, kv_block):
   fully visible -> no mask; fully future -> skip; diagonal -> per-row lane
   predicate. Sliding window is the same test on the lower bound. Strictly
   better than llama.cpp's mask DMA and matches nntrainer's "don't compute"
   semantics.
6. **Decode:** follow llama.cpp — HVX online-softmax per (token, head) —
   as a later phase. Prefill on HMX first; that is where the 40-60x is.
7. **Seam:** `supports_sdpa_fp16_kvcache()` / `sdpa_fp16_kvcache(...)`
   virtual pair on `ComputeOps` (the `gemm_q4_0_accel_fp32` precedent),
   `HtpComputeOps` override forwarding over FastRPC, `MHACoreLayer` calling
   `context.getComputeOps()` behind a shape gate with CPU fallback.
8. **Device validation is one script** (`run_u8i4_layer_on_device.sh`).
   Every phase builds with `hexagon-clang -Wall -Werror`; pure-logic parts
   are host-unit-tested; the kernels are gated on-device by SNR against the
   f32 reference (> 40 dB) and, for resident tiles, by bit-identity.

## 3. Kernel design

### 3.1 Shapes
Per call: one (batch, layer) prefill step. Inputs: Q f32 `[S][n_head_Q*hd]`
(post-RoPE), K/V cache f16 `[cache_to][n_head_KV*hd]`, `cache_from`
(position of q row 0), `hd % 32 == 0`, `hd <= 256`. Output f32
`[S][n_head_Q*hd]`.

Tiles: 32x32 f16, 2048 B. `g_br = align_up(G*Br, 32)` rows per Q block;
`Bc` multiple of 32 (64 preferred: two K tiles per DMA row group).
Row `r = q*G + g` within a Q block; kv_head `n` outer loop.

### 3.2 VTCM layout (single planner, host-checkable)
```
Q_ah      [g_br/32][hd/32]            tiles     (per Q block, per kv head)
Kt_wh x2  [hd/32][Bc/32]              tiles     (K^T, double buffer)
V_wh  x2  [Bc/32][hd/32]  col-tile-major        (double buffer)
S_ah      [g_br/32][Bc/32]                      (Q.K^T out, f16)
P_ah      same as S (in place)
D_ah      [g_br/32] diagonal tiles              (rescale)
O_wh  x2  [hd/32][g_br/32] col-tile-major       (ping-pong, feeds back as weight)
Dinv_ah   [g_br/32]
m, l      f32 [g_br]                            (running max / sum)
K_land x2 [Bc][hd] f16   raw DMA landing (K rows, natural orientation)
V_land x2 [Bc][hd] f16
cfg_f16   hexkl_micro_hmx_config_size()         (setup_acc_read_f16)
```
Worked size, G=4, hd=128, Br=16 (g_br=64), Bc=128: ~420 KB. VTCM is not
the constraint; the pipeline depth is.

### 3.3 Per (kv_head n, Q block) loop
```
prep Q_ah: f32 -> f16 * (scale*log2e), GQA row gather, vshuff(-2) interleave
m = -inf, l = 0, O = 0
for kv block b in visible range:            (skip fully-future blocks)
  DMA K rows -> K_land, V rows -> V_land     (one 2D descriptor each,
                                              row = hd*2 B, stride = n_kv*hd*2)
  Kt_wh <- transpose+interleave(K_land)      HVX vscatter, fused transpose
  V_wh  <- interleave(V_land) col-tile-major
  acc_clear_f16; for kt in hd/32: mm_f16(Q_ah[kt], Kt_wh[kt]) ; acc_read_f16 -> S_ah
  HVX softmax on S rows (f16 in, qf32 sums):
     diagonal block: lane mask on cols > pos(r); window lower bound
     rowmax over unmasked lanes only; m_new = max(m, rowmax)
     P = exp2(S - m_new) (clamp -24), rowsum; l = l*exp2(m - m_new) + rowsum
     D = diag(exp2(m - m_new)) written as AH tiles; m = m_new
  acc_clear_f16
  for rt: mm_f16(D[rt], O_wh_prev[rt])       (rescale, weight = previous O)
  for ct: mm_f16(P_ah[ct], V_wh[ct])          (accumulate P.V)
  acc_read_f16 -> O_wh_cur ; swap
Dinv = diag(1/l); O_out = Dinv . O ; acc_read -> ah ; vdeal(-2) -> rows
f16 -> f32, scatter rows q*G+g to out[q][(n*G+g)*hd]
```
Notes:
- `acc_read_f16` writes AH layout; AH == WH per tile for f16, so O_wh is
  consumed as the weight operand next iteration without relayout.
- The O accumulation over `[D.O_prev | P.V]` is one accumulator pass:
  clear once, `hd/32`... tiles of D.O then `Bc/32` tiles of P.V, read once.
- Masked lanes: set S to -inf **before** the max, never let them reach exp.
- Row range for softmax splitting across the worker pool: rows are
  independent (own `m`, `l`, D diagonal entry).

### 3.4 What HexKL gives vs what must be hand-written
| need | HexKL | hand-written |
|---|---|---|
| tile MAC | `hexkl_micro_hmx_mm_f16` | — |
| acc read (AH f16) | `hexkl_micro_hmx_acc_read_f16` | — |
| acc clear / config | `acc_clear_f16`, `setup_acc_read_f16` | — |
| Q rm->AH with f32->f16, scale, GQA gather | (`rm_to_ah_f16` is f16-only, fixed tile) | HVX vshuff(-2) fused |
| K^T -> WH | (`rm_to_wh_f16` reads DDR only, no transpose) | HVX vscatter, from K_land |
| V -> WH col-tile-major | (`copy_psubmatrix_to_f16_weight` is DDR-only) | HVX vshuff(-2), from V_land |
| diagonal AH tile | none | 32 scalar->stack then vector copy (avoid scalar VTCM writes) |
| exp2 f16 / reductions | none | port llama.cpp `hvx_vec_exp2_f16`, reduce_max_f16, reduce_sum_f32 |
| AH -> rows f16->f32 | `ah_to_rm_f16` (fast, fixed tile) or vdeal(-2) | vdeal + hvx f16->f32 |

Correctness of the hand-written layouts is checked on device against
HexKL's own `rm_to_ah_f16` / `rm_to_wh_f16` / `ah_to_rm_f16` as oracles
(probe test), the same way the prior branch ramp-probed the int32 layout.

## 4. Phases

Each phase: builds with `-Wall -Werror` via `test/htp/build.sh`; has a
gtest with host reference; on-device run is one script.

### Phase 0 — f16 bring-up and probes (this branch, small)
- Session: add `setup_acc_read_f16` config region; check `hmx_fp16_rate`,
  return `AEE_EUNSUPPORTED` if 0.
- IDL `probe_f16_layouts`: verify (a) AH==WH per-tile for f16 on v79,
  (b) `acc_read_f16` tile == `rm_to_ah_f16(reference)`, (c) hand-written
  vshuff/vscatter tilers == HexKL tilers. Any mismatch stops the plan.
- Host: unit tests for the VTCM planner, causal block-range logic, and a
  scalar f32 reference of the online algorithm.

### Phase 1 — single-thread fp16 FA-2 on HMX (prefill)
- `hmx/hexkl_attn_f16.{c,h}`: planner + the loop in 3.3, K/V from DDR via
  `hexkl_dma_ring` (synchronous), softmax on the caller thread.
- IDL `attn_f16_prefill(S, cache_from, cache_to, n_head_q, n_head_kv, hd,
  window, q_f32, k_u16, v_u16) -> out_f32`; DSP `HAP_perf` timing of
  Q.K^T / softmax / O-update / store as separate fields.
- gtest `unittest_hvx_attn_f16.cpp`: f32 host reference (mirror of
  `mha_core.cpp:42-101` semantics incl. head-minor layout), SNR gate
  (expect > 60 dB against an fp16-accumulation model, > 40 dB vs f32),
  shapes: decode-like S=1..4, S=32 single block, S=128 multi-block with
  diagonal blocks, GQA G in {1,2,4,8}, hd in {64,128}, window set/unset.

### Phase 2 — HVX parallelism and the optional terms
- Softmax and the D/Dinv builds across `hvx_worker_pool` by row range
  (>= 16 rows, else inline — the prior branch's threshold).
- Attention sink and logit softcap (both are in nntrainer models:
  GPT-OSS, Gemma): sink seeds `m = sink*log2e`, `l = 0`; softcap
  `tanh(S/c)*c` before the max.
- Decode path: HVX online softmax per (token, head), fp32 accumulator
  (llama.cpp `flash_attn_ext_f16_thread`), split across the pool by
  (token, head). Gate: `S < 5 && hd <= 128`.

### Phase 3 — pipelining and resident KV tiles
- K/V DMA depth-2 prefetch (ring already chains descriptors), landing
  buffers x2, tile buffers x2.
- `hvx_worker_pool_submit/wait` (async job) so HVX softmax(b) overlaps HMX
  Q.K^T(b+1); HMX stays on the FastRPC thread (single HMX owner, same as
  today). Measure; llama.cpp's separate HMX thread only if this caps out.
- "NativeKV": `kv_append_f16` IDL entry that tiles new K^T/V rows into
  resident WH tile buffers in DSP heap at append time (32-row aligned
  blocks; tail block masked), so per-step K/V staging becomes a 2 KiB-row
  DMA of ready tiles. Tutorial ch06 and the prior branch both measured
  this as the long-context win.
- Bc/Br chooser with llama.cpp's cost model, re-calibrated on device.

### Phase 4 — nntrainer integration and E2E
- `ComputeOps`: `supports_sdpa_fp16_kvcache()` + `sdpa_fp16_kvcache(...)`
  (explicit pointers/strides; no Tensor types in the signature).
- `HtpComputeOps : CpuComputeOps` in `htp_compute_ops.cpp` forwarding to
  the FastRPC stub; `get_htp_ops()` returns it when the backend is enabled.
- `MHACoreLayer::one_batch_incremental_forwarding`: behind a gate
  (`S >= 5 || hd > 128`, fp16 cache, B == 1, hd % 32 == 0) replace steps
  2-4 with the seam call; otherwise unchanged CPU path.
- KV cache in `rpcmem` (external-cache mode of `MHACoreLayer`) so the DSP
  reads DDR directly instead of FastRPC copying the used range per call.
  Done as `ComputeOps::alloc_shared` -> `HtpBackend::alloc_shared`
  (`rpcmem_alloc`, cached heap) -> `KVCacheManager::setSharedAllocator`,
  selected by `"attention_engine"` in the model config. No IDL change:
  rpcmem registers its blocks with FastRPC, so the existing buffer
  arguments are passed by mapping whenever they point into one. Device
  numbers in the status header; test `HtpSharedKvCache` in
  `unittest_hvx_attn_f16` gates on bit-identity and reports the times.
  What is left of the per-call cost is FastRPC's cache clean of the whole
  used range; `remote_register_buf_attr` with `FASTRPC_ATTR_KEEP_MAP` /
  `FASTRPC_ATTR_FORCE_NOFLUSH` plus a manual flush of only the rows
  written since the last call would take that further, at the price of
  owning cache maintenance ourselves.
- E2E: CausalLM prefill benchmark on the same GGUF-equivalent model
  llama.cpp reports (Qwen3-0.6B/1.7B), pp128 tok/s, attention-only
  breakdown from the DSP timers. Target: attention block within 1.5x of
  llama.cpp's `-fa on` HTP path on the same device.

## 5. Risks
- **AH != WH for f16 on v79** would break the O feed-back trick. Phase 0
  probe (a) tests it; fallback is an `ah_to_wh` relayout per block on HVX.
- **fp16 O accumulation** across many KV blocks: llama.cpp accepts it; the
  gtest's fp16-model SNR gate quantifies it; fallback is an fp32 O in HVX
  (the decode path's design) at the cost of leaving HMX for the rescale.
- **FastRPC transport** ~170 us/call measured on the prior branch. Phase 4's
  rpcmem cache removes the copy; per-layer call count is inherent until a
  persistent batched skel exists (out of scope here).
- **hexagon-clang re-types spilled splat constants.** llama.cpp's
  `hvx_vec_exp2_f16` feeds a hand-encoded qf16 coefficient (0x5082) into a
  qf16*qf16 multiply. Inlined into a big kernel, the compiler spilled that
  splat, reloaded it as "hf" and selected the mixed qf16*hf instruction,
  so E5 became 36.06 and every probability gained ~36*f^6 (bit-exact
  scores, ~20 dB outputs; the same function in a small probe compiled
  correctly, which is what made this hard to see). `hvx_attn_exp2_hf` now
  states the types itself: the E5 term is an fp16 constant through
  `Q6_Vqf16_vmpy_Vqf16Vhf`. Rule for this codebase: never put a
  hand-encoded qf16/qf32 constant into a qf*qf multiply; give the compiler
  an hf/sf constant and the mixed intrinsic.
- **qf32 * qf32 is not exact about zero.** The decode kernel's rescale
  `O *= 2^(m-m')` on a still-zero O accumulator produced ~1e30 in every
  lane whenever the factor was nonzero (only reachable with a sink, whose
  logit seeds m before the first block). O is now an IEEE f32 accumulator
  (widen p*v to qf32, add the sf sum, round back), and the rescale is
  sf*sf. Anything that multiplies two qf32 values where one may be an
  exact zero has the same exposure.
- **Strict aliasing.** Scalar stores into a stack array followed by a
  punned `*(HVX_UVector *)` load are UB and hexagon-clang does reorder them
  at -O3; every such load/store in these kernels goes through the
  memcpy-based `hvx_tile_load_u/store_u`.
