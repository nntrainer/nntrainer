01 · Run it: from a clean clone to a token on the phone

Six stages, in the order the project's own verification ladder uses them (skill hexagon-gates, HEXAGON.md §5). Stages 1–4 run on your Mac inside a container and need no phone. Stage 5 is a file you hand to the person with the phone. Stage 6 is the app switch. Nothing here is a build log: these are the commands as the scripts and docs define them.

Who runs what

docs/plans/0000-agent-system-and-env.md §2 "Machines and the measurement loop"; tools/docker/README.md (host-path table).

Stage 0 · One-time container setup: tools/docker/setup_wizard.sh

The wizard walks through the five things only a person can do and checks each; re-running it skips finished steps. You can run one step by name: setup_wizard.sh sdk. What each step does (from the script):

StepWhat happensWhat you may be asked for
1/5 runtimeChecks docker info and that a linux/amd64 container runs (the image is x86-64; on Apple silicon it runs under emulation).Install OrbStack (brew install --cask orbstack) or Docker Desktop with Rosetta enabled.
2/5 imageBuilds nntrainer-hexagon-dev:ubuntu24.04; downloads Android NDK r26d (~1 GB, 10–20 min).Patience.
3/5 sdkInstalls the Hexagon SDK (6.4 or newer) with Qualcomm's package manager (qpm-cli) inside a throwaway container into ~/Qualcomm/Hexagon_SDK/<ver>/. The SDK is licensed and is mounted, never baked into the image.The Linux x86 .deb of Qualcomm Package Manager 3 saved into ~/Qualcomm/downloads, and your Qualcomm login. Product name hexagonsdk6.x; newest version unless QPM_SDK_VERSION is set.
4/5 modelDownloads the public Qwen/Qwen3-0.6B files (~1.5 GB) into Applications/CausalLM/res/qwen3/qwen3-0.6b/hf, then builds the int8 checkpoint nntr_qwen3_0.6b_w8cx_DEFAULT.bin with tools/hexagon/make_w8cx_bin.py, the W8_CX .bin producer on this branch (numpy only; same primitive and tensor order as nntr_quantize --fc_dtype W8_CX on the hvx_m3 branch, which is not here) (~2 min). The size, 598,230,528 bytes, is the hard gate; the script then prints md5 … and warns WARN: md5 differs from the #23 baseline (7562313bb4cc70410450d0ab3a4fa563) if it is not the baseline's — another HuggingFace snapshot legitimately gives a different md5 at the same size, a stale or partial file does too, so read the warning as "check which", not "broken" (HEXAGON.md §2.4, §5.1; setup_wizard.sh).Nothing.
5/5 checkPrints the SDK and NDK paths seen inside the container, builds the x86 tools and runs the lowering and checkpoint-reader tests.Nothing.

After that, tools/docker/run.sh <command> runs any command inside the container with the repo mounted at /work, the SDK at /opt/qcom/Hexagon_SDK and the model directory read-only at /model. It passes through the environment variables HEX_ARCH, HEX_EXTRA_CFLAGS, SIM_TIMING, NNTR_NUM_THREADS, NNTR_REQUIRE_SDK and HEXAGON_SDK_VERSION. The container entrypoint sources the SDK's setup_sdk_env.source, so HEXAGON_SDK_ROOT, DEFAULT_HEXAGON_TOOLS_ROOT and DEFAULT_TOOLS_VARIANT are set; the compiler is not on PATH, the scripts call it by full path.

tools/docker/setup_wizard.sh, tools/docker/run.sh, tools/docker/README.md, tools/docker/Dockerfile (NDK r26d, API 31, ncurses 5 for the SDK 6.4 simulator). Toolchain inside the SDK: hexagon-clang 19.0.04, toolv19 (HEXAGON.md §5.2).

Stage 1 · x86 reference run (no SDK, seconds to minutes)

Before any DSP code, the project has a plain-C scalar version of every kernel (test/hexagon/sim/ref_ops.c) and a program, hexagon_ref_run, that interprets a packed weight image with them. It is the accuracy oracle: the same fp16 + per-token int8 math the DSP does, run slowly and exactly on x86 (HEXAGON.md §5.1).

tools/docker/run.sh ./tools/hexagon/build_host_x86.sh
tools/docker/run.sh ./build_x86_hexagon/test_lowering                  # LOWER_TEST PASS
tools/docker/run.sh ./build_x86_hexagon/test_w8cx_bin /model/nntr_qwen3_0.6b_w8cx_DEFAULT.bin   # W8CX_BIN_TEST PASS
tools/docker/run.sh bash -c 'gcc -Wall -Werror -o /tmp/t test/hexagon/test_oplist_header.c && /tmp/t'

# pack the image (~2 s) and make a token file, then evaluate
tools/docker/run.sh ./build_x86_hexagon/nntr_hexpack /model/nntr_qwen3_0.6b_w8cx_DEFAULT.bin /work/build_x86_hexagon/qwen3_full
tools/docker/run.sh python3 tools/hexagon/make_tokens.py /model/hf text.txt /work/build_x86_hexagon/t.i32 --limit 512
tools/docker/run.sh ./build_x86_hexagon/hexagon_ref_run /work/build_x86_hexagon/qwen3_full --tokens /work/build_x86_hexagon/t.i32 --eval
  • nntr_hexpack <bin> <prefix> [--layers N] [--max-seq N] [--max-chunk N] writes <prefix>.hexw (the weight image, 598,623,744 bytes for the full model, 172,498,944 for --layers 1) and <prefix>.hexcfg (12 key=value lines) — HEXAGON.md §2.4; the --max-seq / --max-chunk options are in hex_pack.cpp.
  • --eval prints a teacher-forced perplexity (PPL) and a top-1 hit count. Reference values to compare against: the 512-token local prompt gives PPL 33.0195 / top-1 184 on the workstation's gcc build (HEXAGON.md §5.1, re-run 2026-09-17). Note that the number can depend on the host compiler: on a different 512-token prompt the container's clang build gave 41.2365 / 161 and the workstation's gcc 13 build 41.5466 / 164, 0.75 % apart with no DSP involved (HEXAGON.md §5.1; 23-sdk64-baseline.md "Accuracy"). Always quote which build produced a reference.
  • Other modes: default (prefill in chunks, then greedy --steps N), --dump-op i --dump-out f, --list-ops (HEXAGON.md §5.1).

Stage 2 · Simulator golden tests (needs the SDK; tens of minutes under emulation)

The Hexagon simulator (hexagon-sim) boots a small real-time OS image (QuRT) and runs one named test that compares each DSP kernel against ref_ops.c. A pass prints SIM_TEST <name> PASS (HEXAGON.md §5.2).

HEX_ARCH=v75 tools/docker/run.sh ./tools/hexagon/build_sim_test.sh     # -> build_hexagon/sim/libnntr_sim_test.so
HEX_ARCH=v75 tools/docker/run.sh ./tools/hexagon/run_sim_test.sh profile acc   # the per-task gate
for t in smoke pool exp quant matmul matmul_dma rmsnorm rope eltwise embed attn logits graph; do
  HEX_ARCH=v75 tools/docker/run.sh ./tools/hexagon/run_sim_test.sh $t || break
done
tools/docker/run.sh ./tools/hexagon/run_sim_test.sh hmx     # the 14th test since #68 (v79 default): needs HexKL on the mount, else "SIM_TEST hmx SKIP: built without HTP_HMX", rc 2
  • Budget. Under Rosetta on the Mac, profile acc takes about 10 min and the 13 tests about 5 min (HEXAGON.md §8.3 SDK 6.4 re-run: 10m23s and 4m13s; skill hexagon-gates). Run profile acc per task and the 13 tests once before a PR; if no DSP file changed, skip both and say so. Since #68 the sweep also runs hmx when HexKL is mounted (it is counted as the 14th, and a SKIP is never a pass); a change that touches only hmx/ or test_hmx.c runs hmx per step and the 13 + hmx once before the PR (skill hexagon-gates rung 3).
  • Expected on this branch. Both arches pass 13/13 and profile acc: on v79 (the gate, the default of build_sim_test.sh / run_sim_test.sh since #35) profile_prefill_acc STAT max_abs=0.0659682 max_rel=92.7791, quant_generic 0/65536, every matmul_w8a8_* / matmul_dma ref_* / logits STAT 0/0; on v75 (fallback, HEX_ARCH=v75 on both commands) 0.0757427/66.5909. Before #35 the same sources on v79 gave 9 PASS / 4 FAIL (quant, matmul, matmul_dma, logits, all ±1 LSB), traced to one sign bug in the quantiser decode and fixed by an integer decode (HEXAGON.md §5.2, §7 rule 6, §8.3 "#35 re-run"). Since #25 (PR #61, merged) the sweep also prints SIM_TEST matmul_dma prefetch hits=6 workers=6 and leaves every STAT bit-identical — the prefetch cannot show in the simulator because it does not model DDR (HEXAGON.md §8.3 "#25 re-run"). Since #68 (PR #72, merged 2026-09-21) build_sim_test.sh prints HexKL: /opt/qcom/hexkl_addon/lib/hexagon_toolv19_v79/libhexkl_micro.a (HTP_HMX=1) when the addon is mounted, and the 14th test hmx passes on v79 with SIM_TEST hmx lock rc=0 acc_layout usable=1 base=0 row_stride=32, hmx_mm_copy / hmx_mm_inplace / hmx_mm_reloc STAT max_abs=0 and wh_reloc bytes_same=1: the plain -mv79 simulator core (v79na_1, HMX v3) executes HMX bit-exactly, so HMX numeric tests are simulator gates like the other 13 (HEXAGON.md §5.2, §7 rule 11). The 13 HVX STATs and profile acc are bit-identical in the HexKL build (the arena sits above the HVX slabs; HEXAGON.md §2.2). Without HexKL the test prints SIM_TEST hmx SKIP: built without HTP_HMX and returns 2.
  • Never use SIM_TIMING=1 at model shape: a timing run was aborted after 30 minutes without producing its first result line (HEXAGON.md §5.2). Simulator cycles are a correctness gate and a relative signal only; they do not model DDR bandwidth (HEXAGON.md §8.3; plan 0000 §2 gap rule 1).

Stage 3 · Build the DSP library (skel) and the phone-side harness

tools/docker/run.sh ./tools/hexagon/build_skel.sh                   # -> build_hexagon/skel/libnntr_htp_skel.so (v79, the default)
                                                                    #    prints "HexKL: … (HTP_HMX=1)" when the addon is mounted (#68)
HEX_EXTRA_CFLAGS=-DHTP_HMX=0 tools/docker/run.sh ./tools/hexagon/build_skel.sh   # the HVX-only skel with HexKL present: object-identical to a tree without hmx/
tools/docker/run.sh ./tools/hexagon/dsp_obj_md5.sh <tree>           # per-object md5 of the DSP sources: the "no DSP bytes changed" proof (#68)
HEX_ARCH=v75 tools/docker/run.sh ./tools/hexagon/build_skel.sh     # the v75 fallback, runs unchanged on v79 silicon
tools/docker/run.sh ./tools/hexagon/build_host_test.sh              # -> build_hexagon/host/{hexagon_rpc_test,hexagon_e2e_test}
  • Name the arch on purpose. build_skel.sh defaults to v79 (HEX_ARCH="${HEX_ARCH:-v79}"), and since #35 (device 2026-09-18) v79 is the shipping skel: it is 10–27 % faster than v75 on the S25 Ultra's v79 cDSP with matching accuracy, and a v79 build with the IEEE float helpers and one with the qf-format helpers gave identical PPL and top-1 on silicon (HEXAGON.md §7 rule 1, §9). v75 stays the fallback, built only when a change touches an __HVX_ARCH__ branch or on request. The #35 kernel fix and the #25 cross-op weight prefetch (PR #61, merged) are both on this branch, so a v79 skel built here is the shipping skel the latest numbers were measured with (54.6 Mcyc per decode step at 512 on unit R3CY10WM83Y, #25 B). Whatever you build, write the arch and the md5 in the handoff; the device records the skel that actually ran (23-sdk64-baseline.md "Skel identity").
  • The script first runs the interface compiler (QAIC) on nntr_htp.idl to generate the stub and skel glue, then compiles executor.c, htp_graph.c, worker_pool.c and every file under ops/, hvx/, dma/ with -mhvx -mhvx-length=128B -O3. It probes -mhvx-ieee-fp on an empty file and prints hexagon-clang v75: -mhvx-ieee-fp probe -> -mhvx-ieee-fp; with HEXAGON_Tools 19.0.04 the flag is accepted (HEXAGON.md §7 rule 4; build_skel.sh). Since #68, when /opt/qcom/hexkl_addon (HEXKL_ADDON_ROOT) carries lib/hexagon_toolv19_v79/libhexkl_micro.a and include/hexkl_micro.h, the script also compiles hmx/*.c with -DHTP_HMX=1 and links HexKL, printing HexKL: … (HTP_HMX=1) and built: … (v79, HTP_HMX=1); otherwise HexKL: not linked (HTP_HMX=0; … absent). Such a skel acquires the HMX unit and a VTCM arena at init() and logs the HexKL version, but runs no HMX kernel yet and its HVX results are bit-identical (02 §6; HEXAGON.md §5.3).
  • Variants for a measurement: HEX_EXTRA_CFLAGS=-D… appends compiler flags to the skel build; copy each result to libnntr_htp_skel.<variant>.so before the next build and record its md5sum (skill hexagon-gates rung 4). The measurement-only flags, all off in the shipping build: HTP_MM_NO_VTCM (weights read straight from DDR, M6), HTP_FORCE_QF_HELPERS (qf-format float helpers on v79, #35), and since #25 (PR #61, merged) HTP_MM_NO_PREFETCH (the cross-op weight prefetch compiled out: the A/B control), HTP_MM_CHUNK_ROWS=<n> (a fixed DMA chunk instead of max-fit), HTP_MM_STREAM_ONLY (every weight byte is DMA'd, nothing is multiplied — a ceiling skel whose outputs are garbage by construction, so no --eval) HTP_PROF_FARF (one nntr_htp: prof … line per call with the DSP cycles split by op kind, summed by tools/hexagon/summ_farf_prof.py), and since #68 HTP_HMX=0 (the HVX-only build even with HexKL on the mount: no hmx/ object, no HexKL symbol, the plain 4 MB VTCM acquire; with the addon mounted the scripts set HTP_HMX=1 themselves). When a PR claims "no DSP bytes changed", the proof is tools/hexagon/dsp_obj_md5.sh run on both trees, not the skel's md5 — the linked .so embeds its random temp object names — and #68 used it to show its -DHTP_HMX=0 build identical to hvx_impl in all 12 objects (HEXAGON.md §3, §5.3; skill hexagon-gates). #25 built four skels this way, A/B/C/D, and ran them as a reversed double pass, and #58's handoff does the same with HTP_ATTN_L2FETCH / HTP_ATTN_NB (HEXAGON.md §5.3 "Measurement-only skel flags"; 25-decode-prefetch.md "Artifacts"; 58-decode-attn-gqa.md "Artifacts" on branch hvx/58-decode-attn-gqa).
  • The skel is not part of the meson build; the host library is (-Denable-hexagon=true, HEXAGON.md §4).

Stage 4 · The handoff: the phone is run by a person

Write docs/measurements/<issue#>-<slug>.md from the template in the hexagon-handoff skill: why, an artifact table (path, md5, commit), the exact commands, the expected log lines, an empty result table with the reference number next to each cell, and the estimated minutes. Commit it on the issue's hvx/<issue#>-<slug> branch and set the label state:needs-measurement. The person then runs, on the workstation with the phone on USB (HEXAGON.md §5.3):

./tools/hexagon/run_device_test.sh [serial]                       # RPC_TEST PASS
python3 tools/hexagon/check_rpc_log.py logs/hexagon/device_test_<stamp>.log
./tools/hexagon/run_e2e_test.sh /tmp/qwen3_full [serial] -- --tokens /tmp/t512.i32 --chunk 128 --steps 64
./tools/hexagon/run_e2e_test.sh /tmp/qwen3_full [serial] -- --tokens /tmp/t512.i32 --eval
  • run_device_test.sh pushes the skel and hexagon_rpc_test and checks the round-trip contract with an empty op-list (session open, shared memory, ABI-mismatch rejection, mapping, a dummy pattern proving host-written bytes are visible on the DSP, 32 timed round-trips). check_rpc_log.py exits 0 only if all six RPC_TEST markers are present (HEXAGON.md §5.3; check_rpc_log.py).
  • run_e2e_test.sh pushes the skel, the harness, the image and the token file only when the device copy's md5 differs (the image is ~600 MB; a size-only check once left a stale image on the phone, HEXAGON.md §5.3 "Pitfall"), writes 0x1f into hexagon_e2e_test.farf so DSP log lines reach logcat, runs with ADSP_LIBRARY_PATH / DSP_LIBRARY_PATH pointing at the pushed directory, and saves logs/hexagon/e2e_<stamp>.log plus device_farf_<stamp>.log.
  • Expected lines: E2E init ok weights=598623744 ..., one E2E step <i> pos=<p> n=<n> pcycles=<c> us=<t> top1=<id> per chunk or decode step, E2E gen ..., E2E wall_ms; for --eval: E2E ppl <x> steps 511 top1 <n> wall_ms <w> (23-sdk64-baseline.md step 3; hexagon_e2e_test.cpp).
  • The person pastes the numbers into the file, commits, and sets state:measured. How to turn the lines into tok/s is on the measure page; the filled numbers end up on 06 · Performance.
  • Name the phone. Two S25 Ultra units have been used and their DSP decode clocks differ (1.91 vs 2.05 GHz), so every handoff and every benchmark row records the unit serial (adb devices), and a speed comparison against another unit is made in DSP Mcycles per step, not tok/s (HEXAGON.md §7 rule 9 (a)–(b)). The first e2e run after a push is cold — rule 9 (d) had it at 3–5 %, and #25 measured +8.5 % DSP cycles on the first run of the day — so any A/B whose verdict is tighter than ±10 % is run twice, A B C D then D C B A, and only pass 2 is read; a warm-up run is not a substitute (rule 9 (d); 25-decode-prefetch.md "Steps", "Notes"). The DSP clock can also wander within one session (1743–2046 MHz across the #25 runs), which is why verdicts are read in DSP Mcycles, not host ms. At 4096 the rule is stricter (rule 9 (e), standing since #53): even the Mcyc figure moves with the session on one unit (+2.2 % between two orders 25 min apart, +4.4 % between two sittings on the same day, +8.6 % against the other unit with the same binary), so a 4096 verdict is an A/B of both skels back to back inside one order after the same idle, never a 4096 cell against another day's row; before each order the handoff records adb shell dumpsys battery temperature and charging status and the idle minutes, and it names the sitting it is read against (HEXAGON.md §7 rule 9 (e); 53-4096-unit-split.md "Steps", "Notes from the run").

Complete, filled examples: docs/measurements/23-sdk64-baseline.md (SDK 6.4 baseline, 2026-09-17, about 20 min of phone time for two skel variants), 24-host-logits.md (a host-only A/B/C with reversed double runs), 35-v79-skel.md (three skels, 15 runs, about 14 min on the device), 25-decode-prefetch.md (four skels A/B/C/D as a reversed double pass at 512 plus B and C at 1024 / 4096, 14 runs, about 15 min) and 53-4096-unit-split.md (two skels at 4096 only, two mirrored orders with a ≥ 10 min idle and a battery-temperature read before each, plus one 4096 --eval per skel, about 20 min device-active / 40 min wall). The next one to be run is 58-decode-attn-gqa.md on branch hvx/58-decode-attn-gqa (four attention skels, ≈ 17 min core + 9 min tail).

Stage 5 · The app switch: "engine": "htp"

The CausalLM app does not go through nntrainer's per-layer engine registry; per-layer remote calls would bring back exactly the overhead the design removes, so the offload is all-or-nothing at the app level (HEXAGON.md §5.4). In nntr_config.json:

{ "engine": "htp", "model_file_name": "nntr_qwen3_0.6b_w8cx_DEFAULT.bin", ... }
  • main.cpp sees engine == "htp" and, only for Qwen3ForCausalLM, calls initHexagon(weight_file) instead of initialize()/load_weight()/repack_weight(). HexagonBackend::create() memory-maps the int8 checkpoint, runs lower_qwen3(), packs the weight image straight into shared memory (no .hexw file), zeroes KV and ACT, and calls HexagonRunner::init() (hexagon_backend.cpp; HEXAGON.md §5.4).
  • If any of that fails the app prints one hexagon: ..., CPU fallback line on stderr and builds the CPU graph exactly as before. Verified messages: hexagon: open failed (0x80000406), CPU fallback with the skel removed; hexagon: w8cx bin: size 2384199680 != expected 598230528, CPU fallback with an fp32 checkpoint (HEXAGON.md §5.4). A failure during generation ends the run with an exception; there is no CPU graph to switch to.
  • Build: tools/package_android.sh . -Denable-hexagon=true -Dhexagon-sdk-root=$HEXAGON_SDK_ROOT, then Applications/CausalLM/build_android.sh --cache (without --cache the app script rebuilds nntrainer without the backend). On the phone the process needs ADSP_LIBRARY_PATH / DSP_LIBRARY_PATH pointing at the directory holding libnntr_htp_skel.so, and a copy of /vendor/lib64/libcdsprpc.so next to the binary; /vendor/lib64 must not be on LD_LIBRARY_PATH (HEXAGON.md §4, §5.4).
  • App-level numbers on record (S25, 18-token prompt, 64 generated): prefill 23.8 tok/s, decode 13.0 tok/s, RSS 758 MB on the DSP path against 52.0 / 18.7 tok/s and 3.1 GB on the CPU fp32 fallback. Those predate the M6 P3/P4 kernels; the harness figures on the index page are the current ones, and HEXAGON.md §9 lists an app re-measurement as planned work (HEXAGON.md §5.4, intro, §9).
