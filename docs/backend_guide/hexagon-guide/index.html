The Hexagon backend, for people who have never touched a DSP

nntrainer can run a small language model (Qwen3-0.6B) on the signal processor (Hexagon cDSP) inside a Snapdragon 8 Elite phone instead of on the phone's CPU. This guide explains how that works, how to run it, and how to read the numbers. Everything here is taken from docs/backend_guide/HEXAGON.md, HEXAGON_BENCHMARK.md, the code under nntrainer/tensor/hexagon/ and Applications/CausalLM/hexagon/, and the filled measurement handoffs under docs/measurements/ (#23, #24 and #35 on this branch; #25 on branch hvx/25-decode-prefetch, PR #61); each number says where it came from.

The one-paragraph mental model

The phone's main processor (the host, an arm64 Android CPU) does three things. First, once at start-up, it converts the model's weights into one big byte image in a memory area both processors can see, and hands that image, an empty key/value cache and a scratch buffer to the DSP together with a short recipe called the op-list (HEXAGON.md §1, §1.1). From then on the DSP owns the whole graph: it keeps the buffers mapped for the life of the session and knows every step of the model. Second, for each chunk of prompt tokens or each generated token, the host sends only the token ids and the position, and the DSP runs the entire recipe in one remote call (one FastRPC round-trip, about 0.26 ms; HEXAGON.md intro, §8 M1 test 231 / 255 / 284 µs min / median / max). Third, the host reads back the logits (one score per vocabulary word, 151,936 floats for this model; HEXAGON.md intro) and picks the next token. There is no per-layer chatter between the two processors, which is the whole point of the design.

Three facts to hold on to

  • Toolchain. Every build happens in the dev container with Hexagon SDK 6.4 (6.4.0.2 in the container; the workstation that built the 2026-09-17 and 2026-09-18 device binaries has 6.4.0.1) and hexagon-clang 19.0.04 (HEXAGON.md §5.2; tools/docker/README.md; 23-sdk64-baseline.md "Artifacts").
  • Wire contract. Host and DSP agree on op-list ABI version 4 (NNTR_HTP_ABI_VERSION in nntr_htp_common.h); init() rejects any other version before touching memory (v5, with the W4 kind and layout ids, exists only on #65 S1's branch, in review). Since PR #50 (issue #36) the same header also holds the one table of operand byte sizes, nntr_htp_op_extent(), that the DSP validator, the x86 reference runner, the simulator reference and the simulator model all read (HEXAGON.md §1, §1.4).
  • v79 is the shipping skel; v75 is the fallback. The S25 Ultra's cDSP is v79 silicon and a v79-native skel is 10–27 % faster there with matching accuracy (#23). Its last simulator discrepancy — four ±1 LSB failures traced to one sign bug in the quantiser decode — was fixed by #35, and on silicon a v79 skel with the IEEE float helpers and one with the qf-format helpers gave identical PPL and top-1, so HEXAGON.md §7 rule 1 is closed and HEX_ARCH=v79 is the default of build_skel.sh. A v79 change still needs both the v79 simulator sweep and a device --eval (HEXAGON.md §7 rule 1, §9). The #35 kernel fix, the v79 default of build_sim_test.sh / run_sim_test.sh and the cross-op weight prefetch that #25 measured (−11.6 % decode cycles at 512; PR #61, merged) are all on this branch, so a skel built from this tree is the one the latest numbers were measured with. The next kernel direction is not HVX at all: issue #65 brings the HMX matrix unit in through HexKL for 4-bit weights. Its build stage S0 (#68, PR #72) is merged: a skel built here with the HexKL addon mounted links HexKL and acquires the HMX unit plus a VTCM arena at init(), but no op uses HMX yet and the HVX kernels' outputs are unchanged bit for bit; its accuracy stage S1 is in review with a failed PPL band (see 06, "What is open").
