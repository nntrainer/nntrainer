04 · Measure and debug: reading the numbers, and finding the op that lies

Four skills: turn a filled measurement file into tok/s you can trust (and know which phone it came from); compare accuracy three ways so a kernel bug cannot hide behind quantization noise; bisect a divergence to one op with find_divergence.py; and read the DSP's own log (FARF) when something fails before any number appears. The numbers themselves are collected on 06 · Performance.

docs/plans/0000-agent-system-and-env.md §2 (gap rules 1–3); skill hexagon-handoff "Reading a filled one".

2 · How to read a measurement handoff

Take docs/measurements/23-sdk64-baseline.md as the worked example. A handoff has five parts; here is what to check in each.

Turning E2E lines into numbers (23-sdk64-baseline.md step 3; HEXAGON.md §8.2 "Throughput by context"):

  • Each chunk or step prints E2E step <i> pos=<p> n=<n> pcycles=<c> us=<t> top1=<id>; us is host wall time around the one RPC, pcycles is the DSP's own cycle count of the op loop.
  • prefill tok/s = prompt tokens ÷ (sum of us over the n=128 steps ÷ 1e6).
  • decode ms/tok = median host us over the 63 n=1 steps ÷ 1000; decode tok/s = 1000 ÷ that.
  • DSP Mcyc/tok = median pcycles of the same steps ÷ 1e6. Effective clock = pcycles ÷ us (the harness prints it as pcycles_per_us); the nominal top corner is 2.09 GHz, but which S25 Ultra unit you hold decides what you actually see — 1884–2064 MHz across the six #23 runs on one unit, 1905–1915 MHz in the generation loop on the other (section 2a below).
  • For --eval: E2E ppl <x> steps 511 top1 <n> wall_ms <w> — teacher-forced perplexity over the prompt and how many next tokens the top-1 prediction got right.

Two caveats you will meet. The 512-token decode median is taken over 63 steps that are still settling after prefill (first-ten vs last-ten median Mcyc 67.1 → 64.3 at 512, flat at 1024 and 4096), so treat that pair as ±5 % by construction; a firmer figure needs repeated medians or a settled-tail estimator. And host wall time can move for host-side reasons the DSP did not cause (P3 → P4 host fell 76.4 → 31.2 ms while the DSP fell 35 → 28.5 ms), so the DSP pcycles are the comparable number between kernel versions (HEXAGON.md §8.2).

2a · Two phones, two clocks: HEXAGON.md §7 rule 9

Two Galaxy S25 Ultra units have been used, and their cDSP holds different clocks in the decode loop. #24 (2026-09-18) found it: with the same v75 kernels as #23 (its skel's DSP diff against #23's is comments, clang-format and one per-call token-id check) the DSP cycles per step agreed within ~1 % at 512 and 1024 (65.1 vs 64.3; 85.0 vs 84.2 Mcyc) while tok/s came out −8 / −1 %. The P4 → #23 512-token "gain" (27.7 → 31.9 tok/s) was therefore the unit, not the SDK: on R3CY10WM83Y P4 ran 68.9 Mcyc in 36.1 ms and #24 65.1 Mcyc in 34.0 ms, both at 1.91 GHz. The rules that came out of it (HEXAGON.md §7 rule 9):

  • (a) Name the unit. Every handoff and every benchmark row carries the serial (adb devices; #23's own file did not, which is why its unit is inferred from the clock — see the footnote on 06).
  • (b) Across units compare DSP Mcycles per step; tok/s bands only within one unit. That makes Mcyc/step the column to read first on the performance page.
  • (c) Read a host-vs-DSP gap against the run's own clock, never the nominal 2090 MHz. At 1.91 GHz a 34.0 ms / 65.1 Mcyc step is a ≈ 0 ms gap, though the nominal formula prints 2.85 ms — this is what kept #24 from opening a DSP top-k method. The same goes for the pcycles_per_us ≥ 2.05 bar.
  • (d) The first e2e run after a push is cold, and the reversed double pass is mandatory for a tight verdict. #24 put the cold run at about 3 % host wall and 5 % DSP cycles high (the first 16 forward_full_us of an hexagon_rpc_test group about 20 % high); #25 (2026-09-18, same unit) measured the first run of the day at +8.5 % DSP cycles over the same skel in pass 2 (66.97 vs 61.74 Mcyc). Read on pass 1 alone, #25's prefetch ratio would have been 0.84 instead of the 0.88 it is, and the chunk-64 variant would have looked 6 % better than it is. So any verdict tighter than ±10 % is read from pass 2 of a reversed double pass — A B C D, then D C B A — and a warm-up run is not a substitute (#24 ran malloc → rpcmem → static, then the reverse: pass 1 spread 1.8 ms, pass 2 spread 70 µs). Within one session the clock can also wander — 1743–2046 MHz across the 14 #25 runs — which is why the host-ms and Mcyc columns can even order two variants differently; verdicts read Mcyc. The teacher-forced --eval loop on the same unit runs at 1167–1178 MHz because the host spends ~10 ms between RPCs (issue #41) (HEXAGON.md §7 rule 9 (d); 25-decode-prefetch.md "Steps" 1–2, "Notes").
  • (e) The 4096 row moves with the unit and the session, not with the code — so a 4096 verdict is an A/B inside one order (the standing rule since #53). The symptom: #35's v79 skel read 188.0 / 186.8 Mcyc (first run / cooled re-run) and 32.1 / 32.7 prefill tok/s on R3CY10WM83Y against #23 B's 177.6 / 34.4 on the other unit (+5.9 / +5.2 %, −6.6 / −4.9 %) while its 512 and 1024 rows sat within 2 %, and #24's v75 row had missed by the same +6.0 % the day before. The test (#53, 2026-09-18): #23 B's exact binary (aba0126e…, fingerprinted by its --eval 1.5687 / 3758) and hvx_impl's skel (1ab00865…, --eval 1.5623 / 3759 = #35) ran 4096 back to back in two mirrored orders on this unit, ≥ 20 min idle and a battery reading before each order. Inside an order the two are indistinguishable (197.285 vs 197.092, 192.905 vs 192.897 Mcyc; same 64 tokens); between the two orders, 25 min apart, every run moved 2.2 %; the four-run mean sits 4.4 % above the same unit's #35 re-run of the same morning and 9.8 % above #23 B — with #23's own binary at +8.6 %. So there is no code regression, the offset is the unit and the session (the phone was charging throughout, and earlier sittings' charge state is not on record — the one variable left unsplit), and the rules are: a 4096 verdict compares both skels inside one order after the same idle (one order resolves 0.1 %); a 4096 cell is never read against another sitting's row, even on the same unit (±5 % between sittings, ≈ +9 % between units with identical bytes); a 4096 handoff records adb shell dumpsys battery temperature (tenths of °C) and status before each order plus the idle minutes, and names its reference sitting; #23 B's 4096 cells stay the other unit's numbers; and a skel's size is not a tree fingerprint (the second skel landed 32 B under a prediction made on another tree) — the --eval digits are. The measurement file itself calls its slot-matched result "inconclusive" (−2.22 % / +2.17 %, just outside its ±2 % band, opposite signs); the supervisor read the opposite signs as the per-order drift, excluded the code outcome and closed #53 without the second-day pair it asked for — see 06, "What each measurement decided" (HEXAGON.md §7 rule 9 (e), §8.2 "#53" block; 53-4096-unit-split.md "Reading", "Notes from the run").

And the 512 caveat again, because it bites here too. The 512 decode median is ±5 % by construction (the 63 steps are still settling), so #35's 512 gate was passed on cycles (+1.8 %) and 1024 / 4096 were read first; a 512 tok/s difference of a few percent between two runs on the same unit says nothing (23-sdk64-baseline.md "Results"; 35-v79-skel.md "Results"). A handoff therefore opens with an environment check: its control variant must land within ±5 % of the unit's last reference at 512 in Mcyc, or the session is void (stale artifact or wrong unit), not a result — #25's control read +0.9 % of #35's 61.2 (25-decode-prefetch.md "Results", "Pass rules").

A ceiling is measured, not derived. To know how fast decode could ever go with the current weight bytes, #25 built a skel with -DHTP_MM_STREAM_ONLY that DMAs every weight byte of the step and multiplies nothing (outputs garbage by construction, so no --eval; it prints nntr_htp: stream bytes/step=595984384). Its per-kind split gives the stream phase — mm8+mm16+lg = 32.2 Mcyc = 18.5 ms at that run's 1743 MHz = 32.3 GB/s = 54 tok/s at 512 — and the rest of its step is the attention and eltwise it still runs. The trap the handoff fell into first: reading mm8+mm16 alone ("≈ 74 tok/s") forgets that the lm_head is 26 % of the bytes; the read-back corrected it (25-decode-prefetch.md "Goal rows"; HEXAGON.md §8.2 "The ceiling (G1'), read correctly").

3 · The 3-way accuracy comparison

  • x86 reference vs simulator — per kernel, on the simulator, with a mixed bound |d| ≤ atol + rtol·|ref|; the integer paths (W8A8, LOGITS, EMBED, the int16 accumulate) must be bit-exact, the float epilogues are allowed one fp16 ulp (2e-3 / 1e-3), the quantizers a bounded ±1 LSB rate. The 8-token profile acc uses the looser 0.1 / 0.1 bound because per-token int8 re-binning amplifies a 1-ulp fp16 difference roughly 2× per layer (HEXAGON.md §5.2).
  • Simulator vs device — the same compiled skel, so a difference is silicon behaviour, a context-ownership bug the simulator cannot see (§7 rule 7), or a stale artifact. This is where the 2026-08 IEEE failures and the 2026-09-17 v79 surprise both showed up; #35 then showed the four v79 simulator failures were a quantiser sign bug and the 2026-08 failures a toolchain artefact (HEXAGON.md §7 rule 1). The standing rule survives both: a v79 change needs the v79 simulator sweep and a device --eval.
  • x86 reference vs device, model level — --eval perplexity on the same image and tokens. On eval.txt (387 tokens) the DSP scored 20.2802 against 20.2718 reference (+0.04 %); with the P4 kernels the gap on the local prompts is +0.16 … +1.29 %, one band, not a regression. Fake-quant W8_CX itself costs about +3.4 % over fp32; that is the design's activation-quantization price, not a kernel error (HEXAGON.md §8.1, §8.2).
  • Three traps. Short-text logit gates between two correct implementations swing by several percent (HEXAGON.md §8.1 first bullet) — judge at the model level. The reference figure depends on the host compiler that built hexagon_ref_run (0.75 % spread between the container's clang and the workstation's gcc on one prompt) — quote the build (HEXAGON.md §5.1). And the perplexity on these prompts responds by ~1 % to sub-1e-3 perturbations, so a 1 % PPL move alone does not identify a bad kernel (HEXAGON.md §8.2).

4 · find_divergence.py: bisect to the first op that disagrees

python3 tools/hexagon/find_divergence.py /tmp/qwen3_full /tmp/t.i32 --serial <serial> --chunk 8
# -> FIRST_DIVERGENCE op=<i> kind=<k> layer=<l> max_abs=.. max_rel=..   or NO_DIVERGENCE
  • The primitive. forward_debug() (ABI v3+) runs ops [0, n) only and returns a byte slice of WEIGHTS / KV / ACT. hexagon_ref_run --dump-op i --dump-out f does the same on x86. "Outputs agree" is monotone in i, so a binary search finds the first bad op (HEXAGON.md §1.4, §6; nntr_htp.idl).
  • Runs on the phone. The script calls run_e2e_test.sh for the device side, so it belongs in a handoff, not in the container. A partial run still updates the KV cache, so debug sessions restart from position 0 (HEXAGON.md §1.4).
  • Tolerance 0.1 by default, deliberately loose: per-token int8 amplifies ~1e-4 fp16 noise 5–8× per matmul (ATTN rel-RMS 1e-4 → next W8A8 3e-3 on the 1-layer image), so a tight tolerance flags two correct implementations as diverged (HEXAGON.md §6).
  • Use a 1-layer image (nntr_hexpack --layers 1, 172,498,944 bytes) for fast iteration. The last op writes LOGITS, which forward_debug cannot dump; judge it by the --eval perplexity of both runners (HEXAGON.md §6).
  • Beyond the first op. The P4 isolation went one step further: it recomputed the reference for one op from the DSP's own input and compared that to the DSP's output — rel-RMS 1.6e-4, max one fp16 ulp — which separates "this kernel is wrong" from "this kernel is fed slightly different numbers" (HEXAGON.md §8.2).

5 · The FARF log: what the DSP says about itself

FARF is the DSP's logging macro; its lines reach Android's logcat only if a file named <binary>.farf containing 0x1f sits next to the binary on the device. Both run scripts write it, then capture logcat -d | grep -i "nntr_htp\|adsprpc\|fastrpc" into logs/hexagon/device_farf_<stamp>.log (HEXAGON.md §5.3; run_e2e_test.sh; run_device_test.sh).

  • Benign lines in every device log (23-sdk64-baseline.md "Notes"): three adsprpc permission warnings (open_shell failed for domain 3, fastrpc_enable_kernel_optimizations failed, Unable to add watcher for /vendor/lib64/rfs/dsp) and the host line hexagon: init failed (0x80000414), host abi v4, dsp abi v0 from the stub's first probe before the version handshake — the "v0" is the rule that output parameters are not copied back on failure (HEXAGON.md §1.3).
  • What a real failure looks like: a hang, a DSP restart (SSR) or a fatal FARF line; the handoff asks the runner to note the last E2E step line and the FARF tail, adb reboot, and continue (23-sdk64-baseline.md step 4). None occurred in the 13 runs of #23, the 11 e2e runs of #24, the 15 runs of #35 or the 14 runs of #25 (whose one new runtime pattern, a DMA descriptor pending across the worker barrier, would have shown as a > 2× step right after the prefill chunks of a prefetch run — none did). One line that looks alarming but is not: remote_handle64_invoke failed … (user err 0x80000414) in the rpc_test log is that test's own ABI-mismatch case and is followed by RPC_TEST PASS (35-v79-skel.md "Notes").
  • Host-side messages from the app go to stderr as hexagon: … (e.g. open failed (0x80000406), CPU fallback); routing them into the nntrainer logger is planned work (HEXAGON.md §5.4, §9).
  • What a rejection looks like on the host. A DSP AEE_EBADPARM reaches the host as 0x8000040E: the bare code 14 plus the 0x80000400 DSP error base FastRPC adds (the same offset makes AEE_EUNABLETOLOAD / AEE_EUNSUPPORTED appear as 0x80000406 / 0x80000414). HexagonBackend::forward pre-checks all token ids of a request on the host and returns that same value, kHexagonBadParm, without any RPC (hexagon_runner.h, static-asserted in hexagon_runner.cpp; hexagon_backend.cpp). Mid-generation the app throws hexagon: forward failed (0x…) — note that causal_lm.cpp formats the number with std::to_string, so this code prints as the decimal -2147482610 after the 0x, not as 8000040E (causal_lm.cpp; HEXAGON.md §1.4, §5.2).

6 · Simulator profiles: relative signal only

run_sim_test.sh profile <acc|prefill0|prefill512|decode512> [n_workers] lowers the qwen3 shape with 2 layers and a 4096 vocabulary and prints SIM_PROF lines: per-op-kind pcycles, one line per op, and the cost of 1000 empty barriers. python3 tools/hexagon/summ_prof.py logs/hexagon/sim_prof_*.log rescales to 28 layers and the full vocabulary and prints a sim-derived ms/token at 2.09 GHz. Those are simulator cycles: the simulator does not model DDR bandwidth, so they rank bottlenecks but never decide a performance question (HEXAGON.md §5.2, §8.3). Example of the ranking they gave: after P3, MATMUL_W8A16 was 55.4 % of simulated prefill at position 512, which made it P4's target; after P4, attention is the largest cost that grows with context (HEXAGON.md §8.3, §9).

A second caveat, from #58 (2026-09-18): the v79 simulator's sixth worker runs at half speed. The decode-attention branch (hvx/58-decode-attn-gqa) had a simulator gate of "op total ≤ 0.6× the old kernel" for attn_decode_p1024; it reads 0.72×. The per-worker timers show why: with six workers, workers 0–4 finish four attention jobs each in 152–167 Kcyc while worker 5 takes 308 Kcyc for the same four, in every configuration tried (the old kernel, the split, the split with l2fetch, the fusion alone) — so the balance the gate was written to check is there on the five other workers, and the simulator floor is not a verdict. Whether the sixth worker is also slow on silicon is not known; the device handoff decides, and if its B attn column lands near 2/3 of A instead of 1/2 at 4096, a per-worker FARF split is the first thing to look at. Rule of thumb for any change that spreads work over the pool: read the simulator's per-worker timers, not only the op total, and let the phone decide the ratio (58-decode-attn-gqa.md "Notes from the run", simulator record; HEXAGON.md §5.2 on simulator cycles).

A third note, from #68 (2026-09-21): the simulator does execute HMX, and bit-exactly. The plain -mv79 core is v79na_1 with an HMX v3 coprocessor; HexKL's own micro-matmul example passes on it and the new hmx test reads max_abs=0 in place, through HexKL's vendor copy and after a VTCM → DDR → DMA → VTCM relocate. So an HMX numeric STAT is a simulator gate like the 13 HVX tests — the plan's fallback of "links and skips, every HMX gate device-only" was not needed. What the simulator cannot vouch for is the layout HexKL's acc_read_int32 lands an int32 result tile in (sim: acc_layout usable=1 base=0 row_stride=32): the first device handoff of any HMX consumer re-reads that line on the silicon before an in-place result is trusted, and a device usable=0 routes that path through the slower vendor copy — a measured cost, never a hang (HEXAGON.md §5.2, §7 rule 11; plan 65 §4 "S0 outcome", §5 risk 1).
