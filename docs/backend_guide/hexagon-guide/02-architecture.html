02 · Architecture: the pieces and the arrows between them

Seven parts, each with a picture. Read them in order: the packer makes the bytes, the image files carry them, the FastRPC session hands them over, the op-list tells the DSP what to do with them, the worker pool and VTCM are how the DSP does it fast, and the ABI version is the promise that keeps both sides honest.

weights / image (fixed for the session) activations, tokens, scratch (change per call) outputs, KV cache, results

1 · The packer: model shape in, byte layout out

Lowering is the step that turns "a 28-layer Qwen3 with hidden size 1024" into a concrete plan: which op runs when, and at which byte offset every tensor lives. It is host-side C++ with no SDK dependency. graph_lowering.h (in the backend) holds the model-agnostic vocabulary — HexModelConfig, HexModelWeights, HexLoweredGraph, align128(), pack_weights(); the Qwen3 recipe lower_qwen3() lives with the app in Applications/CausalLM/hexagon/qwen3_lowering.cpp. A second model would add its own *_lowering.cpp and reuse pack_weights() unchanged (HEXAGON.md §2).

Two consumers pack: nntr_hexpack writes files for the harnesses, and HexagonBackend::create() packs straight into shared memory for the app (HEXAGON.md §2.4, §5.4; hexagon_backend.cpp).

2 · Image files: .hexw and .hexcfg

  • .hexw is the WEIGHTS image exactly as the DSP will map it. Order: embed (int8, tied — also the logits weight), embed_scale, rope_table (fp16 cos/sin precomputed on the host), final_norm, then per layer the seven projections with one fp32 scale per output row and the four norm vectors as fp16. Since ABI v4 every projection except down is stored in a tiled32 order (the same bytes, rearranged into 4 KB tiles of 32 rows × 128 k so the matmul kernel can consume them without reshuffling; see the kernels page) (HEXAGON.md §2.1).
  • .hexcfg is 12 key=value lines: the 11 HexModelConfig fields (n_layers, n_heads, n_kv_heads, head_dim, hidden, ffn, vocab, max_seq, max_chunk, rms_eps, rope_theta) plus weight_layout=tiled32. Every consumer re-runs lower_qwen3() from it, so the image and the op-list cannot drift apart. A file without the layout key is a pre-v4 image and read_hexcfg refuses it (HEXAGON.md §2.4; hex_image.h; graph_lowering.h).
  • The int8 checkpoint the packer reads, nntr_qwen3_0.6b_w8cx_DEFAULT.bin, is header-less, 598,230,528 bytes, tensors in the order embedding, then per layer attn_norm, wq, q_norm, wk, k_norm, wv, wo, ffn_norm, up, gate, down, then output_norm (HEXAGON.md §2.4).

3 · The FastRPC session: hand off once, map forever

  • FastRPC is Qualcomm's remote-procedure-call mechanism between the CPU and the DSP. The interface is written once in nntr_htp.idl (three methods: init, forward, forward_debug); the QAIC tool generates a host-side stub and a DSP-side skel from it at build time, neither is committed (HEXAGON.md §1).
  • Zero-copy buffers. WEIGHTS, KV and ACT are allocated with rpcmem (a dma-buf, memory both processors can address). They cross the boundary once, at init(), as file descriptors; the DSP maps them with HAP_mmap for the whole session. forward() carries only the small token and logits arrays, whose coherency the driver manages (HEXAGON.md §1.1; nntr_htp.idl).
  • Two bring-up lessons baked into the code: a raw fd number means nothing to the DSP until the host registers it with fastrpc_mmap(..., FASTRPC_MAP_FD_DELAYED) (re-registering returns AEE_EALREADY, treated as success so re-init works); and the weights buffer is additionally passed as an in-sequence so the driver flushes the CPU cache once — the DSP ignores the sequence and keeps the mapping. Weight content must be final before init() (HEXAGON.md §1.1).
  • The session opens an unsigned protection domain so no per-device signing is needed; HVX needs no privileges (HEXAGON.md §1.2). Errors come back as AEE codes, offset by FastRPC's 0x80000400 DSP error base (hexagon_runner.cpp); output parameters are not copied back on failure, so a failed init() reports dsp abi v0 — expected, not a bug (HEXAGON.md §1.3; also seen as the benign hexagon: init failed (0x80000414), host abi v4, dsp abi v0 probe line in every device log, 23-sdk64-baseline.md "Notes").
  • HexagonRunner::create() returning nullptr means "no usable DSP"; callers take the CPU path (hexagon_runner.h).

4 · The op-list (ABI v4): 64-byte records the DSP validates once

The op-list is the "recipe": a fixed-size header describing the model shape, then one 64-byte descriptor per op naming the op kind, its m/k/n shape and up to four tensor references (a buffer id plus an offset). The nine kinds (HEXAGON.md §1.4):

kindwhat it computes
EMBEDgather int8 embedding rows from the tiled table, dequantize to fp16
RMSNORMRMS normalisation; with FLAG_PER_HEAD, per-head QK-Norm
MATMUL_W8A8per-token int8 activation × tiled int8 weight (vrmpy), fp16 out
MATMUL_W8A16per-token int16 activation × row-major int8 weight, fp16 out (down_proj)
ROPErotary position embedding on q and k in place, from the precomputed table
ATTNcausal grouped-query attention against the persistent KV cache
SILU_MULSiLU(gate) ⊙ up
ADDresidual add
MATMUL_LOGITSlast token × tied embedding (same tiled kernel), fp32 logits

For qwen3-0.6b lower_qwen3() emits 1 + 16 × 28 + 2 = 451 ops: EMBED, then per layer RMSNORM → three W8A8 (q, k, v) → two per-head RMSNORM → ROPE → ATTN → W8A8 (o) → ADD → RMSNORM → two W8A8 (gate, up) → SILU_MUL → W8A16 (down) → ADD, then a final RMSNORM and MATMUL_LOGITS (HEXAGON.md §2.3).

Validation at init() (nntr_htp_oplist_validate in nntr_htp_common.h) returns 1 for a bad pointer or size, 2 for a bad magic, 3 for a version mismatch (surfaced as AEE_EUNSUPPORTED), 4 for a bad header field including an unknown weight_layout, and 5 for a bad op: unknown kind, unaligned offset, m != 0 on any kind but MATMUL_LOGITS (the row count is always the per-call token count; a descriptor-fixed m would bypass the forward() gates below), k == 0 or k % 128 != 0 on the four weight-reading kinds, k > 16384 for W8A16, n % 32 != 0 on the tiled matmuls, vocab % 32 != 0 for EMBED, n % 64 != 0 for RMSNORM / ADD / SILU_MUL (the kernels load whole 64-half vectors) and n % head_dim != 0 for a PER_HEAD RMSNORM, ATTN.layer >= n_layers, max_seq % 64 != 0, an ATTN in1/in2 (the chunk's fresh K/V rows) or a MATMUL_LOGITS in0 too small for max_chunk rows (that kernel reads row n_tokens − 1 whatever m says), or any other tensor reference that runs past its buffer when sized for max_chunk rows (ROPE's out is in-place, == in0, and not checked separately). Every code but 3 reaches the host as AEE_EBADPARM (HEXAGON.md §1.4; nntr_htp_common.h; executor.c).

One table of operand sizes (PR #50, issue #36, merged 2026-09-17). The byte extent behind every "sized for max_chunk rows" clause above comes from a single per-kind table, nntr_htp_op_extent(header, desc, rows, &e) in nntr_htp_common.h: given the row count, it fills how many bytes each of in0, in1, in2, out must cover (with a used bitmask and an out_alias_in0 flag for ROPE's in-place output). The validator calls it with rows = max_chunk; hexagon_ref_run --list-ops / --dump-op, the simulator reference ref_graph_forward and the simulator's hand lowering sim_model call it with the call's n_tokens — so the four cannot disagree about an operand size, and find_divergence.py, which parses the dump's bytes= line, follows automatically. Next to it live the row rule nntr_htp_op_rows(d, n_tokens) (d->m ? d->m : n_tokens, which the DSP kernels' htp_m() also uses), nntr_htp_kv_bytes() and nntr_htp_oplist_bytes() (used by lower_qwen3() and sim_model), and a second small header, nntr_htp_rope.h, holds the one RoPE cos/sin row generator nntr_htp_rope_row_f32() shared by the host packer and ref_ops.c. It was a pure refactor: no op-list byte, image byte, validator verdict or STAT moved and the ABI stayed at 4 (HEXAGON.md §1.4, §3; docs/plans/36-op-shape.md; nntr_htp_common.h; test/hexagon/test_oplist_header.c).

Checks at forward() (htp_graph_forward_upto in htp_graph.c): the runtime arguments (token count 1…max_chunk, position + count ≤ max_seq, logits length == vocab) and then every token id (< vocab as one unsigned compare, so a negative id fails too), all before any buffer pointer or KV row is touched; a violation returns AEE_EBADPARM with no FARF line. The same predicate, nntr_htp_token_ids_ok() from nntr_htp_common.h, runs on the host in HexagonBackend::forward over the whole request before the first RPC, because the DSP rejects per chunk and the chunks before a bad id would already sit in KV; the host returns kHexagonBadParm = 0x8000040E, which is AEE_EBADPARM (14) plus the 0x80000400 DSP error base FastRPC adds to every DSP-originated AEE code (hexagon_runner.h, static-asserted against AEEStdErr.h in hexagon_runner.cpp; the familiar 0x80000406 / 0x80000414 are AEE_EUNABLETOLOAD / AEE_EUNSUPPORTED offset the same way). The m == 0, k > 0, n % 64, PER_HEAD, ATTN.layer, ATTN in1/in2, LOGITS-row and token-id rules were added after the 2026-09-17 review (issue #33, PR #44) without an ABI bump: they only refuse lists and calls no kernel could have run safely (HEXAGON.md §1.4, §5.2; hexagon_backend.cpp).

5 · The worker pool: one thread per vector unit, a barrier per op

  • htp_graph runs the ops sequentially; inside each op the work fans out over a pool of QuRT threads, one per HVX vector unit (wp_create(n <= 0) asks qurt_hvx_get_units()), and returns at a barrier. Kernels split rows (matmul: whole 32-row tiles per worker) or heads (attention: by KV head) (HEXAGON.md §1; worker_pool.h; hvx-matmul.c; hvx-attn.c).
  • HVX code may only run on pool workers. Each worker locks a 128-byte HVX unit at thread entry and keeps it for the session, so the RPC thread owns none; locking one there deadlocks. Even the single-row quantization for MATMUL_LOGITS goes through the pool. The simulator does not enforce this, so only a device run or a review catches it (HEXAGON.md §7 rule 7).
  • HMX instructions are issued by worker 0 only (HEXAGON.md §7 rule 10, since #68 / PR #72, 2026-09-21). The HMX lock (HAP_compute_res_hmx_lock) is per thread, so it is not taken on the RPC thread at init: worker 0 takes it lazily on its first HMX section (htp_hmx_worker_acquire, which also sets HexKL's int32 accumulator read up once) and htp_graph_destroy releases it from worker 0 in a wp_run job before the compute-resource context goes back. A future HMX kernel runs its HMX section on worker 0 and fans the HVX epilogue out to the other workers, never the reverse (hmx/htp_hmx.h; htp_graph.c).
  • Cost: an empty barrier is about 4.1–4.3 k simulator cycles per op, ≈ 0.93 ms per decoded token over 451 ops (sim-derived, not device time; HEXAGON.md §8.3). The simulator exposes 4 units on v75 and 6 on v79; the device count is not recorded (HEXAGON.md §5.2, §8.3).

6 · VTCM and DMA: streaming weights past the vector units

  • VTCM is a small, very fast memory local to the DSP. At init() the graph asks for 4 MB best-effort; if it cannot get it (or the build sets HTP_MM_NO_VTCM) the matmul reads weights straight from DDR with bit-identical output. In a build with HexKL linked (-DHTP_HMX=1, since #68) the request is 8 MB plus the HMX unit in one compute-resource context, with 4 MB as the floor — see the HMX arena bullet below. The W8A8 / LOGITS kernel splits the VTCM evenly per worker and uses each slab as a two-chunk double buffer of whole 32-row tiles, kicking the DMA for chunk c+1 while computing chunk c; a chunk is as many tiles as fit in half the slab ("max-fit"). Activations are not copied into VTCM: the quantized rows are read with 4-byte scalar loads, which VTCM would not speed up (HEXAGON.md §2.2; hvx-matmul.c).
  • Cross-op prefetch (issue #25, merged in PR #61). In decode a tiled matmul is only 1–2 chunks per worker, so its first DMA was fully exposed and the memory bus sat idle through the small ops in between (ROPE, ATTN, ADD, RMSNORM, SILU_MUL). #25 gives each worker one DMA queue for the whole session (4 descriptors deep, HTP_MM_DMA_QUEUE_CAP, created at graph init and drained before VTCM is released) and makes the two halves of a slab op-independent, so that when a worker's last chunk of one matmul has landed it kicks chunk 0 of the next tiled matmul (the graph precomputes a next_mm[] table) into the half it is not using; the next matmul finds that chunk already in flight. The same bytes land in the same VTCM bytes, so the output is bit-identical by construction, and the simulator checks the hand-over on an X → Y chain (SIM_TEST matmul_dma prefetch hits=6 workers=6). The int16 down_proj is skipped by the chain because it does not use VTCM. Compile-time knobs for measurements: HTP_MM_NO_PREFETCH, HTP_MM_CHUNK_ROWS=<n> (fixed chunk; 0 = max-fit, the default), HTP_MM_STREAM_ONLY (HEXAGON.md §2.2, §5.2, §5.3; hvx-matmul.c, htp_graph.c).
  • What it buys on the device: the M6 double buffer alone ~5 % on decode and nothing on prefill (1024-token run: decode 90.7 ms with VTCM vs 95.1 ms direct DDR; prefill 44.8 s vs 45.1 s) (HEXAGON.md §8.2 "VTCM/DMA double buffering"). The cross-op prefetch, measured in #25 (2026-09-18, unit R3CY10WM83Y, pass 2 of a reversed double pass): the W8A8 matmul share of a 512-context decode step fell from 24.3 to 16.1 Mcyc (−34 %) and the step from 61.7 to 54.6 Mcyc (−11.6 %), which is 0.5 Mcyc below the pure DMA wait of a skel that streams the same bytes and multiplies nothing — so at 512 the int8 multiplies are now hidden behind the weight stream, whose ceiling is 54 tok/s (596 MB per step at 32.3 GB/s). At 1024 and 4096 the prefetch changes nothing because attention is 46 % / 79 % of those steps (issue #58). A fixed 64-row chunk was tried and rejected (+9.9 % cycles): the small decode ops become several chunks and pay the DMA latency each time (HEXAGON.md §8.2 "#25"; 25-decode-prefetch.md "Pass rules").
  • The int16 down_proj kernel (W8A16) does not use VTCM yet; the simulator cannot say whether streaming would help because it does not model DDR bandwidth, but #25's stream-only skel now has the device number: the row-major down rows move at 21 GB/s where the tiled DMA ring reaches 37, about 3 Mcyc of the decode step — issue #59 (HEXAGON.md §2.2, §8.2 "#25", §9).
  • The HMX arena (issue #65 S0 = #68, merged 2026-09-21 in PR #72; -DHTP_HMX=1 builds only). When libhexkl_micro.a is on the addon mount, the build scripts set -DHTP_HMX=1, compile hmx/*.c and link HexKL, and htp_graph_init asks the compute-resource manager for 8 MB of VTCM (HAP_compute_res_attr_set_vtcm_param_v2, 4 MB floor) plus the HMX unit (HAP_compute_res_attr_set_hmx_param) in one context. The HVX tiled kernels keep exactly the first 4 MB and their slab geometry, so their outputs are unchanged by construction (#68's profile acc STAT is bit-identical to #25's; §7 rule 10 (c): a moved HVX slab is a bug, not a tuning). hmx/htp_hmx.c lays HexKL's arena over the rest: the config region (256-aligned) at the top, two 8 KB int32 result tiles below it, and everything under free_off free for a future kernel's activation tiles and weight strips, every offset 2048-aligned. A 4 MB grant carves only the arena's fixed part (≈ 20 KB) off the HVX region; a refused HMX attribute falls back to the plain 4 MB acquire with ctx.hmx.base == NULL, and an op that needs HMX then fails at init, never running silently on HVX. The worker DMA queues learn the whole VTCM range so a descriptor into the arena carries the bypass bit. init logs nntr_htp: hexkl <version> hmx=<0|1> vtcm_hvx=<B> hmx_arena=<B> (HexKL 1.0.0-beta1 hexagon v79 in the container; the v79 simulator grants 8 MB: 4 MB + 4 MB). A -DHTP_HMX=0 build, or a tree without the addon, compiles none of this and every DSP object is md5-identical to the tree before #68 (tools/hexagon/dsp_obj_md5.sh). No op uses the arena yet (HEXAGON.md §2.2 "HMX arena", §5.3, §7 rule 10; htp_graph.c; hmx/htp_hmx.h; build_skel.sh).
  • Where this picture goes next (issue #65: S1 in review, S2 / S3 planned). The top goal ports upstream PR nntrainer/nntrainer#4327's W4 path: the six per-layer projections move from the HVX vrmpy kernel to the HMX matrix unit with 4-bit weights, fed by the same per-worker DMA queue; the image gains a w4cx layout and the op list a MATMUL_W4A8 kind under ABI v5 (S1, branch hvx/69-w4cx-producer-abi5, in review — its x86 accuracy band failed, PPL 2.05 × W8 against a ≤ 1.10 × gate, so the format is pending a user decision; see 06, "What is open"). Everything on this page stays valid for the W8 image, which must remain byte-identical through the port (plan docs/plans/65-w4-htp-port.md §2–§4, on hvx_impl).
  • The ACT buffer holds nine 128-byte-aligned slots (x, t, q, kb, vb, ao, h2, g, u), each sized for max_chunk tokens and reused by every layer, so it is ~4 MB regardless of depth. The KV cache is separate and DSP-private: 2 × n_layers × n_kv_heads × max_seq × head_dim × 2 bytes, K stored transposed per layer/head so the attention kernel streams 64 positions per vector (HEXAGON.md §2.2).

7 · The ABI version: the promise between two compilers

  • nntr_htp_common.h is plain C compiled by both toolchains (and by the x86 tests); it pins NNTR_HTP_ABI_VERSION 4, the 64-byte record sizes (checked at compile time), the buffer and kind enums, the tiled32 index function nntr_htp_tile_off(), the validator and, since PR #50, the operand-size table nntr_htp_op_extent(), the row rule and the KV / op-list size helpers (section 4 above). The host packer, the DSP kernels and the scalar references all use that one index function, so no two of them can disagree about where a weight byte lives (HEXAGON.md §2.1; nntr_htp_common.h).
  • What v4 changed: a reserved header word became weight_layout and must read TILED32 (1); the tiled matmuls require n % 32 == 0 and EMBED requires vocab % 32 == 0; W8A16 is exempt from tiling but since M6 P4 must have k ≤ 16384. v3 had added the DSP cycle count on forward() and the forward_debug() partial-run primitive (HEXAGON.md §1.4).
  • v5 is proposed, not merged: #65 S1 (branch hvx/69-w4cx-producer-abi5, in review) bumps to v5 with the MATMUL_W4A8 kind and the W4CX_DOWN8 / W4CX layout ids; hvx_impl, and every number in this guide, is v4 (plan 65 §2.2; HEXAGON.md §1.4 on that branch).
  • Rule for any layout or ABI change: bump the version, make .hexcfg reject old images, and update HEXAGON.md §1.4/§2 in the same PR (skill hexagon-gates, kernel review list).
