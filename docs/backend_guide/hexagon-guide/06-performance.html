How to read the rows (method)

  • One harness, one recipe. Every row is hexagon_e2e_test --chunk 128 --steps 64 on a packed qwen3_full image (qwen3_full4k, packed with --max-seq 4224, for the 4096 row). Decode tok/s is 1000 ÷ the median host wall time (µs around one RPC) over the 63 single-token steps after the prompt; prefill tok/s is prompt tokens ÷ the summed wall time of the 128-token chunks; DSP Mcycles per step is the median of the DSP's own cycle counter over the same 63 steps (HEXAGON_BENCHMARK.md "Method"; HEXAGON.md §8.2 "Throughput by context").
  • Two phones, two clocks — and one phone, many clocks. Two S25 Ultra units have been used. R3CY10WM83Y (P3, P4, #24, #35, #25) held 1905–1915 MHz in the generation loop through #35; the #23 unit R3CY205ZMND held 2054 MHz. With the same kernels the DSP cycles per step agree within ~1 % at 512 and 1024, while tok/s differ by −8 / −1 %. In #25 the clock of the same unit wandered between 1743 and 2046 MHz from run to run, so the host-ms column and the Mcyc column even disagreed on the order of two variants. So tok/s is compared only within one unit and session; DSP Mcycles per step is the number to compare across units and across sessions (HEXAGON.md §7 rule 9 (a)–(b); HEXAGON_BENCHMARK.md "Method"; 25-decode-prefetch.md "Notes").
  • An A/B verdict needs the reversed double pass. The first run after a push is cold: rule 9 (d) had it at 3–5 %, and #25 measured the first run of pass 1 at +8.5 % DSP cycles over the same skel in pass 2 (66.97 vs 61.74 Mcyc). Read on pass 1 alone, the prefetch would have looked like −16 % instead of the −11.6 % it is. Every verdict tighter than ±10 % is therefore read from pass 2 of a run that goes A, B, C, D and then D, C, B, A; a single warm-up run is not a substitute (HEXAGON.md §7 rule 9 (d); 25-decode-prefetch.md "Steps" 1–2, "Notes").
  • The per-kind split (HTP_PROF_FARF). A skel built with -DHTP_PROF_FARF prints one nntr_htp: prof … mm8=… mm16=… lg=… attn=… rest=… line per forward call (kilo-cycles spent in the W8A8 matmuls, the int16 down_proj, the lm_head, attention and everything else); tools/hexagon/summ_farf_prof.py takes the median over the decode steps. All four #25 skels carried the flag so its cost cancels in every ratio; the shipping build does not (HEXAGON.md §5.3 "Measurement-only skel flags"; 25-decode-prefetch.md "Artifacts"; both on hvx_impl since PR #61).
  • The 512 decode figure is ±5 % by construction. Its median is taken over 63 steps that are still settling after the prefill (first-ten vs last-ten step median 67.1 → 64.3 Mcyc at 512, flat at 1024 and 4096), so treat a 512 decode difference under 5 % as noise (23-sdk64-baseline.md "Results"; HEXAGON.md §8.2 caveat paragraph). #25's environment check used the same band: its control had to land within ±5 % of #35's 61.2 Mcyc on the same unit, and did (+0.9 %).
  • The 4096 row moves with the unit and the session, not with the code (rule 9 (e), the standing rule since #53). On R3CY10WM83Y the 4096 cell read about +6 % cycles / −6 % prefill against every other 4096 reference, on v75 (#24) and v79 (#35) alike. #53 (2026-09-18) ran #23 B's exact v79 binary next to hvx_impl's skel on this unit: inside one order the two are indistinguishable (0.10 % and 0.004 %, same 64 generated tokens), #23's own binary reads +8.6 % over its number on the other unit, the two orders 25 min apart differ by 2.2 % for both skels, and the four-run mean sits 4.4 % above the same unit's #35 cooled re-run from the same morning. So: a 4096 verdict is an A/B inside one order (both skels back to back after the same idle; one order resolves 0.1 %), never a 4096 cell against another sitting's row; a 4096 handoff records dumpsys battery temperature and charging status before each order plus the idle minutes, and names the sitting it is read against; the between-sitting spread on one unit is ±5 % and the cross-unit offset at 4096 is ≈ +9 % with identical bytes, so #23 B's 4096 cells stay the other unit's numbers and every 4096 goal check is read on the unit that runs it. A skel's file size is not a tree fingerprint (S2 landed 32 B under a prediction made on another tree); the --eval PPL / top-1 digits are (HEXAGON.md §7 rule 9 (e); 53-4096-unit-split.md "Reading"; HEXAGON_BENCHMARK.md "Method").
  • PPL / top-1 come from hexagon_e2e_test --eval: teacher-forced perplexity over the prompt and the count of next tokens the top-1 prediction got right. Two 512-token prompts exist: the P4 prompt t512.i32 (x86 reference 33.0195 / 184, the accuracy gate) and t512_23.i32 (x86 41.5466 / 164 with the workstation's gcc build, 41.2365 / 161 with the container's clang build — quote the build). The 1024 / 4096 prompts have no x86 reference (23-sdk64-baseline.md "Accuracy"; HEXAGON.md §5.1). A stream-only skel (#25 C) has no --eval: its outputs are garbage by construction.
  • What the goals are read against (user decisions of 2026-09-18). The stage-1 W8A8 decode goal is no longer a fixed tok/s. Every HVX goal is read relative to nntrainer's own CPU baseline — Qwen3-0.6B on the S25 Ultra CPU from main, precision Q4_0-FP16 — which issue #60 measures (handoff docs/measurements/60-cpu-baseline.md, pending); a goal that is a multiple of that baseline is written as the multiple plus the tok/s it resolves to once the row is filled. The provisional ≥ 60 tok/s was withdrawn because it sits above the measured 54 tok/s weight-stream ceiling; the ceiling stays the physical bound any multiple must respect. Two more decisions the same evening: the A8W8 HVX-only line (stages 1–2) ends with the issues already filed (#26, #41, #57, #58, #59, #60), HMX for that line comes later; and the new top goal is stage 3, issue #65 (p0): port upstream PR nntrainer/nntrainer#4327's W4 path (HMX u8×i4 matmul, DMA ring, u8 attention, KV quantisation) into this backend's structure and measure Qwen3-0.6B end to end, read against GENIEX_QAIRT w4a16 on the Galaxy S25 (8,207 / 121 at 512, 7,503 / 112 at 1024, 3,546 / 57.6 at 4096, prefill / decode tok/s) with the #60 CPU row as the floor. #51 (the HVX 4-bit stream) is folded into #65 as its decode path (HEXAGON_BENCHMARK.md "Goals" stage-1 W8A8 and stage-3 rows, CPU row, log 2026-09-18 "User decisions (evening)"; plan 65-w4-htp-port.md §1, §7).

What each measurement decided

M6 P4 (2026-09-16) — the kernel set is complete and exact to its definition. The int16 down_proj kernel matched a reference recomputed from the DSP's own input to one fp16 ulp (rel-RMS 1.6e-4); the DSP-vs-x86 perplexity gap of +0.16 … +1.29 % across prompts was isolated to the upstream ATTN/W8A8 qf32 chain, not to the new kernels, and became the accuracy band later handoffs gate on. Decode time on the DSP fell 2.5–2.8× against P3; the host wall fell further than the DSP did for reasons not investigated, which is where the rule "the DSP pcycles are the comparable number" comes from (HEXAGON.md §8.2 "M6 P4 on device").

#23 (2026-09-17) — no SDK regression; v79 is data, not a default. Variant A (v75, SDK 6.4.0.1) matched P4 within −1.6 … −0.6 % on prefill and at or above it on decode, with the P4 prompt at +0.21 % against x86, so ledger ⑭ (SDK 6.4) closed. The 512 decode pair was found to be ±5 % by construction, which became a standing caveat. Variant B (v79-native skel) ran the full set with no hang, no DSP restart and no fatal FARF line, 10–27 % faster than v75 with PPL and top-1 tracking A at every context — while the same build failed four simulator tests by ±1 LSB. Standing rule from it: a v79 change is judged by both gates; the shipping skel stayed v75 until ledger ④ was answered, and issue #35 was told to re-read its plan against these numbers (23-sdk64-baseline.md "Results", "Accuracy"; HEXAGON.md §7 rule 1 update, §8.2).

#24 (2026-09-18) — the logits return is not a lever; ledger ⑫ closed. The 607,744-byte logits return costs about 2.5 ms in an empty call (removed by mapping the rpcmem buffer once with FASTRPC_MAP_STATIC) and less than 0.1 ms inside a real 34 ms decode step, where malloc, rpcmem and static land within 70 µs of each other with byte-identical generated ids and PPL. The harness and HexagonBackend ship the static path on the strength of the isolated number; no DSP top-k / argmax method (ABI v5) is opened, because its trigger had been written against the nominal 2090 MHz clock and the same-minute malloc run showed the gap to be this unit's 1.91 GHz clock. Two by-products: the two-unit / two-clock rule (HEXAGON.md §7 rule 9, with "compare Mcycles across units" and "run sub-ms A/Bs twice with reversed order, read the second pass") and issue #41's opening number (1.17 GHz under --eval). The decode budget was sent to the weight stream (#25, then #51) and to #41 (24-host-logits.md "What the rules yield"; HEXAGON.md §8.2 "Host path" verdict, §9).

#35 (2026-09-18) — the v79 flip is accepted; §7 rule 1 closed; the 4096 drift goes to issue #53. B1 (v79 shipping skel) passed the ±5 % speed gate at 512 and 1024 and the t512_23 accuracy gate, and "Now" in the benchmark moved to its rows. B2 (qf helpers forced on v79) reproduced B1's PPL and top-1 digit for digit within 0.5 % speed, so the 2026-08 IEEE-helper failures were a toolchain-8.x artefact and rule 1's open question closed. Two misses were ruled not to hold the flip: the 4096 cells (+5.9 / +5.2 % cycles, −6.6 / −4.9 % prefill against #23 B on the other unit) repeat #24's v75 miss on this unit the day before with a DSP diff of comments and one token-id check, so they are attributed to unit / session and tracked as issue #53 (rule 9 (e)); and the P4-prompt band 33.07–33.45 had been set from v75 records only, so 32.4497 / 184 is re-baselined as the v79 accuracy record (band ±0.3 %, top-1 184 ± 4), with the 1.7 % v79-vs-v75 offset sent to the layer-0 bisection of #26 (ledger ⑮). Read within the unit and the day, v79 is still 17 % fewer decode cycles and 29 % more prefill than v75 at 4096 (35-v79-skel.md "Verdict", "Notes"; HEXAGON.md §7 rule 1 "Closed", §8.2 "#35" verdict, §9).

#25 (2026-09-18) — the W8 weight stream is finished at 512; the next decode lever is attention; ledger ① and ⑨ closed. The cross-op prefetch cut the decode step from 61.7 to 54.6 Mcyc at 512 (B/A 0.884, −11.6 %, well inside the ≤ 0.90 gate) and the W8A8 matmul share from 24.3 to 16.1 Mcyc (−34 %) — 0.5 Mcyc below the pure DMA wait of the stream-only skel for the same bytes, so at 512 the int8 multiplies are now entirely hidden behind the weight stream and the prefetch build's stream phase (33.6 Mcyc) is within 4 % of the ceiling's (32.2). Prefetch is therefore on by default (G1 PASS). The 64-row chunk (D) read +9.9 % cycles over B with lower prefill, so the max-fit chunk stays (D FAIL); accuracy was unchanged to the digit across A, B, D and both passes (G3 PASS). The ceiling (G1'): every weight byte of the step, 595,984,384 B, streams in 32.2 Mcyc = 18.5 ms = 32.3 GB/s, a 54 tok/s bound at 512 and ≈ 54–57 at every depth; the handoff's first "≈ 74" had left out the lm_head's 26 % of the bytes and was corrected at the read-back. Because 54 is below the provisional ≥ 60 goal, that goal was withdrawn, and the user then decided (issue #60) that every HVX goal is read relative to nntrainer's own CPU baseline instead of a fixed tok/s. What the per-kind split says about the rest: at 1024 and 4096 the prefetch build equals the stream-only skel within 0.1 / 1.2 % because attention is 46 % / 79 % of those steps (34.2 / 146.6 Mcyc, ≈ 6.5 GB/s over the fp16 KV cache, a fifth of what the weight DMA reaches) — issue #58 (balance the 8 kv heads over the 6 workers, share K^T across the GQA pair at m=1; gate: attention halved at 4096) is the first decode lever from here. Two smaller findings became issues too: the row-major down_proj rows stream at 21 GB/s where the tiled ring reaches 37 (issue #59, ≈ 3 Mcyc of the step) and the int16 kernel's epilogue folds exactly four rows, so MM16_R is pinned to 4 by a static check until issue #57 generalises it (that issue also inherits the MM_TB / MM16_TB prefill sweep, inert at m=1). The 4-bit stream of #51 buys 8.3–9.6 ms/step at these rates, which is not enough for 70.3 on its own, so its targets need #58 as well (25-decode-prefetch.md "Pass rules", "Notes"; HEXAGON.md §8.2 "#25" verdicts and "The ceiling (G1'), read correctly", §9; HEXAGON_BENCHMARK.md "Goals" and log 2026-09-18).

#53 (2026-09-18) — the 4096 spread is the unit and the session, not the code; issue closed, no bisection, no re-baseline; rule 9 (e) becomes a standing rule. The handoff's own gate table returns "outcome 3, inconclusive" by the letter: the slot-matched deltas are −2.22 % and +2.17 %, just outside its ±2 % band and with opposite signs. The supervisor read the substance instead: opposite signs of equal size are a per-order drift (every run in order 2 was 2.2 % faster than every run in order 1, while the two skels agree to 0.1 % inside each order), the code / build outcome is positively excluded (#23 B's exact binary never came near its 177.6 on this unit — 197.3 and 192.9, +8.6 %), and the bisection the plan had prepared (1bbd8d53 → #35 / #50 / #33) is not opened. A second-day pair, which the handoff asked for before any re-baseline, was judged not worth a sitting: it would only buy a re-baselined #23 4096 cell that no open verdict needs, because #58's 4096 gate is an A/B inside one order and the decode @4096 goal is 2.5× away, far outside the ±5 % session spread. What changed in the rulebook: a 4096 verdict is read inside one order, a 4096 handoff records battery temperature, charging status and idle minutes before each order (the phone was charging throughout #53, and #23 B's / #35 B1's charge state is not on record — the one variable left unsplit), the cross-unit 4096 offset of ≈ +9 % with identical bytes is a documented property of R3CY10WM83Y, and a skel's file size is no longer trusted as a tree fingerprint — the --eval digits are. The measurement file's "rule 9 (e) stays open, one more pair" and the supervisor's "closed as completed" are the same data read at two levels; this page follows the supervisor's fold, which is what HEXAGON.md and HEXAGON_BENCHMARK.md carry (53-4096-unit-split.md "Verdict", "Reading", "Notes from the run"; HEXAGON.md §7 rule 9 (e), §8.2 "#53" block, §9; HEXAGON_BENCHMARK.md log 2026-09-18 "#53").

Goal policy (2026-09-18, user decisions, issues #60 and #65) — HVX goals are read against nntrainer's own CPU; the A8W8 HVX-only line is wrapped up; the top goal is the W4 port. After #25 showed the fixed ≥ 60 tok/s W8A8 goal to be above the physical ceiling, the replacement proposed by the supervisor (a fixed ≥ 40) was dropped: the stage-1 W8A8 decode goal, and every other HVX goal, is now a multiple of what nntrainer itself reaches on the S25 Ultra CPU from main with Qwen3-0.6B. The same evening the user fixed that baseline's precision to Q4_0-FP16 (#60 unblocked; handoff docs/measurements/60-cpu-baseline.md, still to be run), decided that the A8W8 HVX-only line ends with the issues already filed (#26, #41, #57, #58, #59, #60) with HMX for it later, and opened issue #65 (p0) as the new top goal: bring upstream PR nntrainer/nntrainer#4327's W4 path (HMX u8×i4 matmul, DMA ring, u8 attention, KV quantisation) into this backend's structure and measure Qwen3-0.6B end to end, read against GENIEX_QAIRT w4a16 on the Galaxy S25 with the #60 row as the floor. A stage-3 row was added to the goals; #51's HVX w4g128 plan is folded into #65 as its decode (m=1) path, re-based on the per-channel w4cx format. Until #60 is filled the W8A8 goal cell reads "pending #60", and the 54 tok/s ceiling remains the bound any multiple must respect (HEXAGON_BENCHMARK.md "Goals" stage-1 W8A8 and stage-3 rows, the CPU row, log 2026-09-18; plan 65-w4-htp-port.md §1, §7).
