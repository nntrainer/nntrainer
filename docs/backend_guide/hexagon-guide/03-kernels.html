03 · Kernels: what the DSP actually computes, and why it is written this way

Four kernels carry almost all of the time, plus one helper that feeds them. Each section says what the math is, how the vector unit does it, what it bought, and where the number comes from. The last section explains the project's most surprising rule — float arithmetic only in Qualcomm's "qf" format — in plain words.

weights (int8, fixed in the image) activations (quantized per token, change every call) accumulator lanes / outputs

Quantization in one paragraph

The model's weights are stored as 8-bit integers with one floating-point scale per output row ("W8", per-channel; the checkpoint format is called W8_CX). Activations — the numbers flowing between layers — are fp16 and are converted to 8-bit integers on the fly, one scale per token ("A8", per-token dynamic quantization), right before each matmul. The matmul then multiplies integers, which the vector unit does very fast and exactly, and only at the end multiplies the integer sum by the two scales to get back a float. One layer, down_proj, keeps 16-bit activations instead ("A16") because 8 bits lose too much there (HEXAGON.md §1.4, §2.3, §7 rule 8).

1 · W8A8 tiled vrmpy matmul (q, k, v, o, gate, up and the logits)

  • The layout does the work. An int8 [N][K] weight is stored as 4 KB tiles of 32 rows × 128 k. Inside a tile, vector g holds bytes [4r, 4r+3] = w[nt·32 + r][kt·128 + 4g .. +3]. One vrmpyacc of that vector against a 4-byte broadcast of the activation adds a 4-product partial sum into each of 32 int32 lanes, one lane per output row. After the tile's 32 vectors and all k-tiles, every lane is a finished dot product. A whole n-tile's K strip (32·K bytes) is contiguous, so one DMA descriptor streams it (HEXAGON.md §2.1; nntr_htp_common.h; the interactive picture is docs/superpowers/specs/hexagon-hvx-optimization/02-tiled-weight-layout-why.html).
  • Exact integers, then two multiplies. Integer sums are exact in any order, so they match the scalar reference bit for bit. The epilogue converts with Q6_Vsf_equals_Vw and multiplies in the reference's order ((float)acc × sw[n]) × sx[t] using qf32 ops, then narrows once to fp16. The qf32 rounding can differ from an IEEE product by one fp16 ulp, which is why the unit tests keep a 2e-3 / 1e-3 bound (HEXAGON.md §7 rule 5).
  • Token blocking. MM_TB = 4: one weight-vector load feeds four vrmpyacc, one per token. It showed only 1.3–3.7 % in the simulator, which does not charge weight bandwidth realistically. On the device it is inert in decode (m = 1: one token, nothing to block), so its sweep is a prefill question and was moved from #25 to issue #57 (HEXAGON.md §8.3, §9; ledger ⑩).
  • Where the kernel stands on the device (#25, 2026-09-18, merged in PR #61). With the cross-op weight prefetch the W8A8 matmuls of a 512-context decode step take 16.1 Mcyc, 0.5 Mcyc less than a skel that DMAs the same weight bytes and multiplies nothing: the int8 multiply is fully hidden behind the weight stream, and the stream itself (596 MB per step at 32.3 GB/s, 54 tok/s) is the bound. What is left in the step is attention (32 % at 512, 79 % at 4096; issue #58), the int16 down_proj below, and eltwise (HEXAGON.md §8.2 "#25"; 25-decode-prefetch.md "Notes").
  • What is meant to replace it for the six projections (issue #65) — and where that stands on 2026-09-21. The user decision of 2026-09-18 ends the A8W8 HVX-only line with the issues already filed and makes the top goal a 4-bit port: the q/k/v/o/gate/up matmuls move to the HMX matrix unit (u8 activation × int4 weight through HexKL, per-channel scales, the w4cx layout) with a new MATMUL_W4A8 kind, while this kernel keeps serving the W8 image and, if HMX turns out to pad a single decode row to 64 at too high a cost, an m=1 HVX W4 variant of it (unsigned nibbles plus an 8·Σx correction, the design #51 had) takes decode. The reference the W4 rows are read against is GENIEX_QAIRT w4a16: 8,207 / 121 tok/s at 512 (plan docs/plans/65-w4-htp-port.md §1, §3, §4). S0 (#68) is merged (PR #72): HexKL is linked, HMX and a VTCM arena are acquired at init, hexkl_acc_tile is ported and the hmx simulator test proves a 64×32 u8 × 32×32 i4 micro-matmul bit-exact on the v79 simulator — but there is still no HMX op kernel; this vrmpy kernel serves every projection and its STATs are bit-identical to before (HEXAGON.md §2.2, §5.2, §7 rules 10–11). S1 (#69) is in review, pending a user decision: on branch hvx/69-w4cx-producer-abi5 the x86 W4 reference exists and is bit-exact against a numpy evaluation, but its accuracy gate failed — per-channel int4 round-to-nearest on Qwen3-0.6B gives PPL 46.2279 / 148 against W8's 22.5282 / 186 (2.052 ×) on a 512-token prompt, where the plan's stop line was 1.25 × even with q/k/v/o kept int8 (Torch fake quant: only gate + up int4 1.280 ×; a per-row clip search 1.196 × for those two alone). Group scales, which #51's w4g128 had as its accuracy insurance, cannot be expressed in HMX's per-channel tiles (HEXAGON.md §8.1 "Per-channel int4" on that branch; plan 65 §3.1, §4 S1). Nothing of S1 is on hvx_impl.
  • What it bought. Simulator, prefill of 128 tokens at position 512: MATMUL_W8A8 938,298,568 → 20,931,069 pcycles (44.8×); decode W8A8 + LOGITS 8,134,596 → 527,389 (15.4×) (HEXAGON.md §8.3 "M6 P3"). Device (S25 Ultra): a 128-token prefill chunk went from ≈ 5.4 s to 736 ms and teacher-forced decode from 156 M to 55.9 M pcycles per step (HEXAGON.md §8.2 "M6 P3 on device").
  • Rows are split across workers in whole tiles; a worker can get an empty range (tested with n = 64 over four workers). MATMUL_LOGITS is the same kernel with m = 1 and fp32 output whose store is unaligned-safe (hvx-matmul.c; HEXAGON.md §5.2).

2 · W8A16 int16 down_proj

  • Why not int8 here. The input of down_proj is the SwiGLU output, which has large outliers; quantizing it per token to int8 costs about 6 % perplexity on its own (x86 breakdown on 128 tokens, reference 20.32: all-int8 21.72, down in fp32 20.38, while making wo, q/k/v/gate/up or the lm_head fp32 helps far less) (HEXAGON.md §2.3).
  • How. The activation row is quantized per token to int16 (absmax / 32767). The kernel unpacks each 128 weight bytes to int16, multiplies lane-wise into int32 with Q6_Ww_vmpyacc_WwVhVh (a lane holds k/64 products of magnitude ≤ 32767 × 127, which stays inside int32 for k ≤ 16384), then folds four rows together with two shuffles and three rotates, converting to fp32 first and folding in qf32. Scaling keeps the reference order, narrowing is one fp32→fp16 step, and no scalar horizontal sum is left. The weights stay row-major [N][K] because this kernel reads whole rows (HEXAGON.md §7 rule 8, §2.1; hvx-matmul.c header).
  • What it bought. Simulator 8-token gate: MATMUL_W8A16 per call 2,445,246 → 683,954 pcycles (3.58×), whole run 6,940,426 → 3,415,503 (2.03×) (HEXAGON.md §8.3 "M6 P4"). Device: 128-token prefill chunk 736 → 478 ms; generation-mode decode 32.0 tok/s host wall at 59.5 M pcycles per step; teacher-forced decode 43.3 M pcycles (HEXAGON.md §8.2 "M6 P4 on device").
  • Two facts from #25 (2026-09-18). The four-row fold in the epilogue is exact for four rows only: a build with MM16_R other than 4 compiled and returned wrong down_proj rows silently, so #25 (PR #61, merged) pins MM16_R to 4 with a static check and issue #57 generalises the fold (R ∈ {2, 4, 8}) before it can be swept. And in the decode step this kernel is 8.6 Mcyc of 54.6 (15.7 %), only 1.35 Mcyc above the time its 88.1 MB of weights take to arrive — because those row-major rows come straight from DDR at 21 GB/s where the tiled DMA ring reaches 37; putting them on the ring is issue #59, worth about 3 Mcyc (HEXAGON.md §8.2 "#25", §9).
  • Accuracy effect. The x86 reference itself moved when the definition changed (fp16 activation → int16): PPL 37.4738 → 37.1629 on the 387-token local prompt (−0.83 %). On the device the kernel is exact to its definition: recomputing the int16 reference from the DSP's own input gives rel-RMS 1.6e-4 with a max of one fp16 ulp (HEXAGON.md §5.1, §8.2).

3 · Attention

  • What it is. For each query token, attention scores every earlier position (causal), turns the scores into weights with a softmax, and mixes the value vectors with those weights. Qwen3-0.6B uses grouped-query attention (GQA): 16 query heads share 8 key/value heads (HEXAGON.md §2.1 shape line; hvx-attn.c).
  • The trick is the K layout. Keys are cached transposed, [head_dim][max_seq] per layer and head, so one 128-byte vector spans 64 positions of a single dimension and the score loop accumulates 64 positions per multiply-accumulate instead of doing a 64-lane horizontal sum per (query, position). That is the M4 → M5 change: at 512 tokens decode went 102.0 → 89.2 ms and no longer depends on position; a 128-token chunk at position 896 fell from 10.8 s to 6.5 s (HEXAGON.md §8.2 first table and bullets). The validator therefore requires max_seq % 64 == 0 (HEXAGON.md §2.2).
  • Where it sits now. After P3 and P4 it is the largest remaining cost at long context and the only one that grows with sequence length (simulator: 27.5 % of prefill at position 512, 16.7 % of decode; HEXAGON.md §8.3 P3 rows). K^T reuse across query rows in prefill is the planned P5 work (HEXAGON.md §9).
  • The kernel also appends this call's k and v into the cache and computes scores in fp32 scratch per worker, narrowing after the exp in place (hvx-attn.c).

4 · The per-token quantizer (quant_row)

  • Why it matters. Before P3 this ran as scalar code, cost ≈ 345 k pcycles for one k = 1024 row, and at m = 1 a single worker ran it alone — it alone kept decode from meeting its target. Vectorizing it closed that gate and took simulated prefill from 18.19 to 7.37 ms/token (HEXAGON.md §8.3 P3 bullets).
  • How it rounds. The vector unit's qf32 format uses "Von Neumann" (jam) rounding, so no qf-only kernel can reproduce lrintf(x × inv) for every input. The kernel adds a magic constant (1.5 × 2^8 for int8, 1.5 × 2^16 for int16) so the integer bits read as a fixed-point product, then finishes the rounding as integer ops. The rounding resolution is 2^-14 of an int8 step (2^-6 for int16), so a small fraction of elements differ from the scalar reference by one LSB: modelled ~3.6e-5 for int8 (observed 0/65536 in test_quant), about 1 % for int16 (observed 167/25600). The tests allow exactly that (HEXAGON.md §7 rules 6 and 8, §5.2).
  • It runs on the worker pool, never on the RPC thread, even for a single row (HEXAGON.md §7 rule 7).

5 · The elementwise kernels

RMSNORM, ROPE, SILU_MUL, ADD and EMBED are cheap by comparison (all together under 2 % of simulated prefill; HEXAGON.md §8.3 P3 rows). Two things about them are worth knowing: they compute in fp32 inside the op and narrow to fp16 once (rule 2 below), and SILU clamps the exponent argument at -g ≤ 80 because layer 27 of qwen3 produces |g| > 250, which overflowed exp(-g) and turned 1/(1+inf) into NaN in the HVX reciprocal (HEXAGON.md §7 rule 3). EMBED reads the tiled table through nntr_htp_tile_off, a gather of K/4 4-byte loads per token, once per forward (HEXAGON.md §2.1).

6 · Why qf-format only — HEXAGON.md §7 in plain words

The Hexagon vector unit (HVX) can do floating-point math in two number formats. One is the ordinary IEEE format everybody uses (Vhf for fp16, Vsf for fp32). The other is Qualcomm's own intermediate format, "qf16" / "qf32", which keeps an extra exponent range and rounds differently; you convert back to IEEE with a _equals_ instruction when you are done. On the 8 Elite silicon this project targets, the IEEE-format instructions were found not to be trustworthy: Q6_Vhf_vadd_VhfVhf returned all zeros, and in a v79-native build Q6_Wsf_vmpyacc_WsfVhfVhf and chained Q6_Vqf32_vadd_Vqf32Vqf32 produced infinities in attention and in the W8A16 dot (also on the v79 simulator, and sensitive to a printf). The rule that came out of it (HEXAGON.md §7 rule 1):

  • Kernels use only qf-format arithmetic — Wqf32_vmpy_VhfVhf, Vqf32_vadd/vsub_VsfVsf, Vqf32_vmpy_VsfVsf, Vsf_equals_Vqf32, Vhf_equals_Wqf32 — and, until #35, the shipping skel was built with HEX_ARCH=v75, which runs unchanged on v79 silicon.
  • A second rule about rounding (§7 rule 2): converting a qf16 product straight to fp16 (Vhf_equals_Vqf16) rounds badly (a v75 simulator probe: correct 57 %, truncated 21 %, worse 21 %), while Vhf_equals_Wqf32 is an exact round-to-nearest-even. So every kernel computes in fp32 inside the op and narrows to fp16 once, the same contract as the scalar reference; truncating at every op boundary instead costs 2.7 % perplexity.
  • The cost of the rule is a small, understood accuracy band: the qf32 chain in attention and the W8A8 epilogue rounds differently from the fp32 reference, and the DSP-vs-reference perplexity gap sits at +0.16 … +1.29 % across prompts. It was isolated on a 1-layer image to that upstream chain, not to the new kernels (HEXAGON.md §8.2 "M6 P4 on device", §9; ledger ⑮).

The 2026-09-17 twist. With the SDK 6.4 toolchain (hexagon-clang 19.0.04) a v79-native skel ran the full 512 / 1024 / 4096 set on the S25 Ultra with no hang, no DSP restart and no fatal log line, tracking the v75 skel's perplexity and top-1 at every context and running 10–27 % faster (prefill +9.7 / +12.0 / +26.9 %, decode DSP cycles −6.5 / −9.1 / −16.6 %). The old infinities did not reproduce. But the same v79 build failed four simulator tests by ±1 LSB (quant, matmul, matmul_dma, logits) — all in qf-only code with no architecture branch — while the ops that do take the IEEE helpers on v79 (attention, elementwise) passed. Standing rule from it: a v79 change is judged by both gates — a ±1 LSB simulator failure does not predict a device failure, and a device --eval match does not clear a failing simulator test (HEXAGON.md §7 rule 1 update, §5.2, §8.2; 23-sdk64-baseline.md).

The 2026-09-18 closure (#35): rule 1's question is answered and v79 ships. The four simulator failures were one sign bug in the quantiser's decode of the rounded product (rule 6), not the IEEE helpers; #35 replaced the qf32 magic-add decode with an integer decode of the sf bits, after which both simulators pass 13/13 (and the v75 int16 rounding became sign-symmetric). On silicon, a v79 skel built with the IEEE helpers (B1) and the same tree built with -DHTP_FORCE_QF_HELPERS (B2, the qf-format helpers forced on the >= 79 target) gave the same PPL and top-1 digit for digit on both 512-token prompts (32.4497 / 184 and 41.4947 / 162) and were within 0.5 % prefill / 0.1 % DSP cycles of each other, in 15 runs with no hang, SSR or fatal FARF line. So the 2026-08 inf / all-zero failures were a toolchain-8.x artefact: with 19.0.04 the IEEE-format path is neither a correctness nor a speed difference on this part. HEX_ARCH=v79 is the shipping build; v75 is a fallback built only when a change touches an __HVX_ARCH__ branch. What B1 = B2 does not explain is why the v79 skel sits 1.7 % below the x86 reference on the P4 prompt where the v75 skel with the same decode sits +0.03 % above it; that lives somewhere in the v79 build outside the helpers (worker count, codegen) and joined the layer-0 bisection of #26 (ledger ⑮). Both the integer quantiser decode in hvx-quant.h and the HTP_FORCE_QF_HELPERS switch in hvx-base.h are on hvx_impl since #35 (HEXAGON.md §7 rule 1 "Closed", §9; 35-v79-skel.md "Notes"; 06 · Performance).

Where the architecture branch lives in the code: hvx/hvx-base.h selects, under __HVX_ARCH__ < 79, qf32-based helpers for fp16/fp32 add, sub, mul and multiply-accumulate; at >= 79 the same helpers call the native IEEE instructions (Q6_Vsf_vadd_VsfVsf, Q6_Wsf_vmpyacc_WsfVhfVhf, …). The quant_row and W8A8 epilogue paths do not go through those helpers; their only arch-dependent instruction is the exact fp16→fp32 widening. The comment at the top of hvx-attn.c ("output is accumulated in IEEE fp32 vector pairs") describes the v79 branch of that helper; on the v75 build the same call is a qf32 add followed by a conversion.
